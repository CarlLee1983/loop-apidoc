loop-apidoc 是什麼？

把「別人給的一堆亂七八糟 API 文件」變成「一份整齊、可驗證的 API 規格書」。

最重要的一條規矩

文件沒寫的東西，就留空白。
絕不猜、絕不用「大家通常都這樣」補上去。

整條產線長這樣

每一關沒過，就停在那一關。不會硬著頭皮往下做。

分工：誰負責讀，誰負責挑毛病

AI 只負責「讀」，判斷合不合格的永遠是程式。所以換一個 AI，結果的合格標準不會跟著變。

最後會拿到什麼

📘openapi.yaml機器看得懂的 API 規格
🇹🇼中文說明文件人看得懂的串接說明
🔗provenance.json每一句話出自哪份文件哪一行
🖥️review.html離線就能翻的審閱頁
✅驗證報告哪裡過了、哪裡有洞
💯品質分數0–100，只是參考，不決定過不過

紅燈與黃燈

看的是「燈的顏色」，不是「哪一條規則」——同一條規則在不同情況下可能是紅燈也可能是黃燈。

做好之後：進保險箱

程式碼是怎麼分家的

🧠domain/名詞與規則的定義。不碰檔案、不上網。
⚖️core/判官：這句話有沒有證據撐住。
🔌adapters/跟外界接觸的插座（讀檔、抓片段）。
🧪evaluation/評測區，永遠碰不到正式資料。

一個貫穿全部的習慣：會寫檔案的地方就那幾個。

其他每個模組都是「輸入什麼、就回什麼」的純函式。哪些檔案有寫入權限被列成一張清單，有測試看著——偷偷多一個寫檔的地方，測試就會紅。
