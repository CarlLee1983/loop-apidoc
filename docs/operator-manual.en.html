loop-apidoc

Architecture boundary: this manual documents the current agent-native CLI compatibility adapter. The stable product core is model/platform independent; see Architecture.

Loop Engineering's source-grounded API documentation pipeline

繁體中文版見 README.md。

loop-apidoc is a repeatable CLI that turns API integration docs of varying format and completeness into consistent, traceable, standardized artifacts:

  • OpenAPI 3.1 YAML (openapi.yaml)
  • Traditional-Chinese Markdown integration guide (api-guide.zh-TW.md)
  • Offline manual review page (review.html): tracks gaps, source conflicts, and unverified facts as governance items; a document that omits a server URL, authentication details, or sandbox credentials is not labelled an integration risk merely because they are absent
  • Source provenance data (provenance.json)
  • Validation and gap report (validation/report.{json,md})

Core principle: supplier sources are the sole authority for normative, provider-documented claims. Anything a source does not state is never inferred; when required information is missing, validation fails and lists the gaps explicitly rather than filling them with conventions. Implementation conformance is a separate empirical, exact-scope axis.

How it works

The extraction engine is the current coding agent itself. Before any agent reads source content, the operator normalizes raw binary inputs, builds the manifest, and runs the deterministic inspect-source-risk gate. Only after that report passes does a Claude Code plugin or OpenAI Codex CLI session follow skills/loop-apidoc/SKILL.md and extract via a read-only subagent fan-out (each subagent only reads files and searches, returning JSON without writing files); the orchestrating agent writes the results into inventory.json + endpoints/*.json, then calls the deterministic CLI assemble to run the back half of plan → generate → validate.

The CLI itself does not create sessions, log in to private sites, or drive a browser — it only assembles and validates after the agent has written the extraction JSON.

An earlier run-agent CLI mode that extracted via the claude -p subprocess was retired in 2026-06 (together with the NotebookLM extraction backend); agent-native is now the only extraction path.

Full pipeline

URL navigation/caching (optional) → preprocess/normalize raw PDF or Word when required → manifest → inspect-source-risk (required, before agent reads) → assess-sources → extraction (agent read-only subagent fan-out, optionally with --focus directives) → verify-extraction → assemble manifest → normalization plan → generate (OpenAPI + Markdown) → validate → correction (agent-driven)

When validation fails, assemble reports the classified issues via --json; correction is agent-driven: guided by the report, the agent re-reads the relevant sources, overwrites the corresponding extraction JSON, and re-runs assemble, for up to 3 rounds. If it still fails after three rounds, or it hits a gap/conflict that cannot be fixed, it reports the gap/conflict instead of filling it in.

Using it with the OpenAI Codex CLI

The same skill can also run under Codex. Codex does not set ${CLAUDE_PLUGIN_ROOT}, so install the CLI as a global command and mount the skill into Codex's skills directory:

# 1. Install the CLI as a global loop-apidoc command
uv tool install --from /path/to/loop-apidoc loop-apidoc

# 2. Mount the skill into Codex (a symlink is enough; edits sync automatically)
ln -s /path/to/loop-apidoc/skills/loop-apidoc ~/.codex/skills/loop-apidoc

SKILL.md auto-detects the environment via the <APIDOC> placeholder: with $CLAUDE_PLUGIN_ROOT it uses the plugin's bundled CLI, otherwise it falls back to the global loop-apidoc. The rest of the flow (extraction → assemble → validate → correct) is identical on both sides.

Installation

Requirements: Python >=3.11, with environments managed by uv.

# Install dependencies

Once installed as a Claude Code plugin, it is usable inside a Claude session with the CLI bundled in the plugin; for Codex, see "Using it with the OpenAI Codex CLI" above.

Providing sources

Before the agent extracts, the operator only needs to have the sources ready:

  1. Put local source files into a source directory (referred to as <SOURCES>).
  2. Acquire public URLs into local HTML, Markdown, or OpenAPI snapshots; only manifest-bound artifacts that pass inspect-source-risk may be read by an agent.
  3. Convert every raw PDF or Word source to UTF-8 Markdown before inspection; raw binary documents fail closed.

No external Notebook to create, no browser login needed — source reading is done by the current agent within the session.

Supported source formats

Markdown, HTML, and OpenAPI JSON/YAML are directly scannable. PDF, Microsoft Word (.docx only), and public URLs are supported only after conversion or acquisition into a manifest-bound local scannable artifact. Legacy binary .doc, spreadsheets (.xlsx/.xls), plain text .txt, and .csv have no preprocessing path, so the manifest recognises the format, reports it as unsupported, and names the next step: re-save a .doc as .docx or PDF, export the sheet you need from a spreadsheet as a Markdown table, rename a .txt to .md, re-save a .csv as a Markdown table, then put it back in sources/ and preprocess again. None of the four will get a built-in converter — the conversion judgement stays with the person who can see the original file (docs/adr/0012-no-converter-for-legacy-word-or-spreadsheets.md).

Usage

The CLI provides source processing, URL evidence, draft extraction, quality and extraction, scheduled source freshness, run processing, Foundry asset governance, and the local human-review review workbench. The day-to-day extraction flow is driven by the skill; each command can also be used standalone.

preprocess — convert PDF/DOCX to scannable markdown

uv run loop-apidoc preprocess --sources ./sources --out ./work/sources_md

PDF uses pymupdf4llm; .docx uses the built-in fail-closed OOXML normalizer. Supported documents preserve headings and tables and write <original-name>.md; the deterministic .source.json sidecar records schema/security-policy versions plus source and normalized names, sizes, and SHA-256 values. Policy limits are 25 MiB compressed, 2,048 archive entries, 10 MiB per member, 50 MiB total uncompressed, and a 100:1 maximum compression ratio. This first slice accepts UTF-8-compatible Transitional OOXML textual DOCX; unsafe ZIP/OPC/XML, macros and active DDE field codes, markup-compatibility alternate content, external relationships, DTD/entities, altChunk, embedded media, material header/footer/note/comment parts, and merged-cell table semantics that cannot be rendered faithfully are rejected before batch outputs are written. Existing Markdown/sidecars, derived-path collisions, and normalization errors are never overwritten and make preprocess exit 2. The DOCX ZIP/XML fallback is adapted from MIT-licensed book-to-skill at pinned revision efda3b2212ce1b2c052126e85e14de40a32442e8; this project has no runtime dependency and does not inherit its EPUB/RTF/MOBI scope. See the third-party notice. Legacy .doc, spreadsheets, plain text .txt, and .csv remain passthrough (copied byte-for-byte, never converted) and need operator-controlled trusted conversion; preprocess prints each one's own next step. Afterwards, build the manifest over the exact --out directory and pass inspect-source-risk before any agent reads it.

Not validated against a real source. None of the thirteen benchmark cases has a Word source, and every DOCX under tests/ is synthesised in tmp_path. This path's evidence strength equals the benchmark's skipped: code that passes on synthetic input, with no supplier Word delivery having gone through end to end. Available but unproven; the label is removed when the first real delivery arrives and becomes a benchmark case.

manifest — build the source manifest

uv run loop-apidoc manifest --sources ./sources-or-file [--url <URL> ...] [--url-coverage <coverage.json>] [--output manifest.json]

Scans local sources, recording relative path, format, size, SHA-256, scan time, whether supported, duplicate determination, and processing status; public URLs additionally record fetch time, HTTP status, and content hash. --sources accepts a directory or one source file; for a file, its parent becomes sources_root and the manifest contains only that file. When --output is omitted, output goes to stdout.

URL navigation and caching — catalog-url / select-url / cache-url-pages / related-url-pages

# Download the entry page only once and build a sidebar navigation index (does not auto-fetch child pages)
uv run loop-apidoc catalog-url --url <entry page URL> --output ./work/url_sources/catalog.json

# Select catalog nodes by explicit scope (downloads no URLs)
uv run loop-apidoc select-url --catalog ./work/url_sources/catalog.json --branch <branch> --term <keyword> --output ./work/url_sources/selection.json

# Cache all catalog pages and build local body/link/entity indexes (no model involved)
uv run loop-apidoc cache-url-pages --catalog ./work/url_sources/catalog.json --output ./work/url_corpus

# Emit candidate page cards from body links and shared entities; this does not authorize model reads
uv run loop-apidoc related-url-pages --corpus ./work/url_corpus/corpus.json --url <page URL> --output ./work/candidates.json

A token-efficient web-doc reading flow: catalog.json is the complete navigation coverage universe; corpus.json embeds no body text, only pointing at local raw/ and body/ files. Candidate cards are routing metadata only. Before any model reads a selected page, materialize its raw HTML or normalized Markdown inside <EXTRACT_SOURCES>, rebuild the manifest, and pass inspect-source-risk; never give an agent an unmanifested corpus body. When the catalog is empty or the document is a single page, use cache-url-entry --url ... --output ...; downloaded HTML can be converted with normalize-html-snapshot --input page.html --url ... --output sources/page.md, which also writes a provenance sidecar.

import-rendered-url — import protected browser-rendered evidence

uv run loop-apidoc import-rendered-url --input ./captures/page.html --url <original URL> \
  --captured-at "2026-07-29T08:30:00+08:00" --capture-method browser_save \
  --sources ./sources --coverage ./work/url_sources/coverage.json [--confirmed-by-user]
uv run loop-apidoc manifest --sources ./sources --url <original URL> \
  --url-coverage ./work/url_sources/coverage.json --output ./work/manifest.json

Use this lane when an interactive browser can render a page that direct HTTP acquisition cannot reach. It preserves the saved HTML/Markdown bytes and writes versioned provenance for the original/canonical URL, capture time/method, and SHA-256 plus a fetched_rendered coverage result. Existing destinations, malformed metadata, and URL/path/method/digest mismatches fail closed. A verified match prevents manifest and assemble from probing that protected origin; no CAPTCHA handling, credential automation, inference, or crawling is performed.

import-supplementary-note — import an excerpt of supplier correspondence

uv run loop-apidoc import-supplementary-note --input ./notes/sandbox-key.md \
  --from "engineer@provider.example" --received-at "2026-08-16T10:00:00+08:00" \
  --subject "How to obtain the test-environment key" --excerpted-by "carl" --sources ./sources

For normative information that exists only in an email or chat message — how the sandbox key is obtained, where the test environment lives, what must be done before go-live — and for the field-mapping spreadsheet a supplier sends alongside the manual (re-save it as a Markdown table and it takes the same path). The command writes the excerpt plus a .source.json sidecar bound to its content (origin, receipt time, excerpter, SHA-256); manifest reads it and marks the source authority: supplementary. A source with no sidecar is always normative.

A supplementary source may be cited, may fill missing, and may make a claim stand. It may not outrank a formal document, may not be indistinguishable from one in a report, and may not support Core's explicit_support — shadow and strict withdraw its support proposal and evidence reference. A claim resting only on such a carrier is named individually in the validation report as a warning-severity SUPPLEMENTARY_SUPPORT and scored under source grounding. These sources are also omitted from record-fingerprint: freshness comparison presumes a source can be re-obtained, and an email has no URL and no version.

The cost you accept: an excerpt is written by a person who may transcribe wrongly or over-read, and the pipeline cannot tell. Recording the excerpter buys accountability, not verifiability. It is the only source class carrying that cost; see ADR 0010. The sidecar read side fails closed: absence means normative, but a sidecar that cannot be read or does not match its source makes manifest exit 2.

snapshot-openapi-url — pin a directly-linked OpenAPI source

uv run loop-apidoc snapshot-openapi-url --url <OpenAPI JSON/YAML URL> \\
  --sources ./sources --coverage ./work/url_sources/coverage.json [--confirmed-by-user]

For cases where a URL already returns Swagger 2.0 or OpenAPI 3.x JSON/YAML directly. The command validates the spec declaration, pins the raw bytes as a local source, outputs the SHA-256, and writes a coverage ledger with method: direct. An existing snapshot and coverage are never overwritten; subsequent manifest and extraction must use the local snapshot.

cache-gitbook-llms / extract-markdown-drafts / scaffold-extraction — deterministic GitBook Markdown

uv run loop-apidoc cache-gitbook-llms --url https://example.gitbook.io/docs \\
  --sources ./sources --coverage ./work/url_sources/coverage.json
uv run loop-apidoc manifest --sources ./sources --url https://example.gitbook.io/docs --output ./work/manifest.json
uv run loop-apidoc inspect-source-risk --sources ./sources --manifest ./work/manifest.json --output ./work/source-risk
uv run loop-apidoc extract-markdown-drafts --sources ./sources --manifest ./work/manifest.json --output ./work/markdown-api-facts.json
uv run loop-apidoc scaffold-extraction --sources ./sources --manifest ./work/manifest.json --output ./work/scaffold

The GitBook command fetches llms.txt once and caches every safe, same-origin, entry-prefix .md URL under the source directory, with URL/SHA-256/timestamp sidecars. Index/collision errors write no partial corpus; page failures stay visible in coverage. Do not inspect drafts or re-read citations until the risk gate passes. Facts and scaffolds are review aids only: copy the scaffold into the work directory, re-read citations, fill gaps, and then run verify-extraction; never pass a fresh scaffold directly to --extraction.

Not validated against a real source. None of the thirteen benchmark cases has a GitBook source, so this path is available but unproven in the same sense as DOCX — its evidence strength equals the benchmark's skipped.

inspect-source-risk — deterministic pre-agent source-risk gate

uv run loop-apidoc inspect-source-risk --sources ./sources --manifest ./work/manifest.json \
  --output ./work/source-risk [--max-bytes 5242880]

Run this after preprocessing and manifest creation, but before any agent reads source content. It scans manifest-bound Markdown, HTML, and OpenAPI JSON/YAML as text in two directions: whether a source can manipulate the agent (risky Unicode, control characters, instruction/control-token patterns) and whether it leaks material to the agent (secrets and personal data). Raw PDF and Word files are deliberately unscannable and reject the gate: convert them to a supported text form first, then rebuild the manifest over those exact bytes. Blocker rules are SR-UNICODE-TAG, SR-BIDI-OVERRIDE, SR-CONTROL-CHARACTER, SR-SECRET-VALUE, SR-UNSCANNABLE, SR-SCAN-SIZE-EXCEEDED, SR-INVALID-UTF8, and SR-FINDINGS-TRUNCATED. Warning rules are SR-BIDI-FORMATTING, SR-ZERO-WIDTH-FORMATTING, SR-INSTRUCTION-OVERRIDE-TEXT, SR-CONTROL-TOKEN-TEXT, SR-CREDENTIAL-REFERENCE, SR-CONTACT-PII, SR-PII-VALUE, SR-PAYMENT-CARD, and SR-WARNINGS-TRUNCATED; warnings are human-review signals, never source instructions to follow.

Among the leak rules only self-evidencing material blocks: SR-SECRET-VALUE is PEM private-key blocks and JWTs, whose structure is the evidence. SR-CREDENTIAL-REFERENCE stays a warning because a competent API document documents Authorization: Bearer <TOKEN>, and whether the value is real cannot be settled from the text — blocking it would reject nearly every qualifying source, and a gate that always needs a waiver is not a gate. Card candidates are Luhn-validated with the card schemes' published test numbers excluded, and a candidate is not a card: the finding is the Luhn-valid window found inside the candidate at digit-group boundaries, because an adjacent number on the same line (1 4539…) otherwise swallows the card into one run that fails Luhn and is never reported. A candidate never spans a line break (joining two adjacent numeric fields passes Luhn roughly one time in ten) but every other Unicode space still separates one.

The command writes source-risk-report.{json,zh-TW.md}, never rewrites a source, and never echoes a matched payload; findings contain only the rule identifier, manifest source reference, and locator. A report retains at most 1,000 findings; additional matches produce the blocker SR-FINDINGS-TRUNCATED. Warnings hold a separate 500-entry budget whose overflow is the warning-severity SR-WARNINGS-TRUNCATED — without that separation, the contact addresses and credential references that are frequent in any large qualifying document would turn the verdict to reject through the truncation blocker, with not one substantive finding in the report. Blockers may still use the whole cap, so warnings never crowd out a real hit. Exit codes: 0 = pass (warnings allowed), 1 = reject (a blocker or unscannable source), 2 = invalid, stale, unsafe, or unreadable input.

assess-sources — pre-extraction source quality gate

uv run loop-apidoc assess-sources --sources ./sources --manifest <manifest.json> \
  --source-risk ./work/source-risk --observations <observations.json> \
  --source-set <name> --output ./work/source-quality [--base-manifest <old manifest>]

Before extraction, assesses source quality against traceable observations, producing source-quality-report.{json,zh-TW.md} and a source diff source-diff.{json,md}, with a verdict of pass or reject. --source-risk is required: the command verifies the binding, re-runs deterministic inspection against the current source bytes, and requires the complete audit to match before embedding it. Blocker observations may list explicit HTTP(S) links in required_source_refs; a rejected report emits their ordered, de-duplicated union as a bounded next-capture seed and never crawls it. Pass the report directory to assemble --source-quality: reject aborts assembly before the run-dir is created; a passing report and source diff are retained in the run-dir for audit.

record-fingerprint / check-freshness / check-freshness-batch — scheduled source freshness gate

uv run loop-apidoc record-fingerprint --run-dir ./output/<run-id> --output ./work/source-fingerprint.json [--force]

uv run loop-apidoc check-freshness --fingerprint ./work/source-fingerprint.json \
  [--sources ./sources] [--json] [--report-dir ./work/freshness]

Once a run has completed or been approved as a Foundry asset, first use record-fingerprint to write a baseline source-fingerprint.json from that run directory (SHA-256 of local sources, plus one version-signal fetch per URL source); an existing file is not overwritten unless --force is given. Afterwards, running check-freshness on a schedule (e.g. cron) cheaply determines whether the sources are worth re-extracting, without re-parsing the whole document or calling any model: OpenAPI URL sources compare info.version (an identical version is treated as unchanged even if the bytes differ), HTML compares ETag/Last-Modified first then falls back to body SHA-256, and local files compare SHA-256. Exit codes: 0 = unchanged (re-parse can be skipped), 1 = changed (re-run extraction), 2 = inconclusive (a source could not be fetched or read). With --report-dir it additionally writes freshness-report.{json,md}; without it, no file is written.

To sweep many docsets at once, use check-freshness-batch instead:

uv run loop-apidoc check-freshness-batch --watchlist ./work/freshness-watchlist.json \
  [--json] [--report-dir ./work/freshness]

freshness-watchlist.json lists multiple watch items, each with a label (identifying name), fingerprint (the source-fingerprint.json path relative to the watchlist file's directory), an optional sources (local source root, likewise relative to the watchlist file), and an optional run_dir (display only). The command runs the same comparison as check-freshness for every item; a fetch or read failure on a single item only marks that item as error and records the reason, without aborting the whole batch; but a malformed watchlist file (invalid JSON or off-schema) fails outright. Aggregate exit codes: 0 = all unchanged, 1 = any changed, 2 = any inconclusive or errored. With --report-dir it additionally writes freshness-scan.{json,md}; without it, no file is written.

To turn the batch result into a bounded human-work trigger, use governance-scan:

uv run loop-apidoc governance-scan --watchlist ./work/freshness-watchlist.json \
  [--json] [--report-dir ./work/governance] [--snapshot-dir ./work/governance-snapshot]

A changed source becomes review_required; an inconclusive or unreadable item becomes attention_required. The command never re-extracts, generates, imports to Foundry, or approves a contract. With --snapshot-dir, changed source bytes from that same scan are retained in an immutable, content-addressed evidence pack: sources/<sha256>.source and governance-snapshot.json. This avoids a second, racy fetch; unchanged, inconclusive, and failed sources are not retained, and an all-unchanged scan creates no empty pack. Exit codes are 0 = no action, 1 = review required, and 2 = attention required.

verify-extraction — check that the extraction JSON meets the contract

uv run loop-apidoc verify-extraction --sources ./sources --extraction ./work [--url <URL> ...] [--focus ./focus.json]

Applies to the agent-produced extraction directory the same input gate as assemble (schema, source citations, cross-file invariants, source facts, deferral phrases, and any v1 evidence[] references). A supplied exact reference must re-materialize from its manifest source with the stated typed locator and normalized-fragment SHA-256, and its claim_path must resolve in the shared normalized-plan projection. The command writes nothing and creates no run directory, making it a fast way to validate the extraction JSON before assembly.

The source-fact gate mechanically scans the manifest's Markdown sources for endpoint declarations, parameter tables and fenced example blocks, then matches them to the extraction by (METHOD, path). When a matched source section documents fields or examples that the extraction dropped, the run fails closed — a silent omission is not the same as "the source does not say so." Naming the field in missing satisfies the gate, so it only ever forces a source-grounded gap, never an invention. Field names are resolved through schema_ref into inventory.schemas transitively, so factoring a shared request body out into a common type counts as deduplication, not an omission.

A companion check rejects placeholder answers that defer the work, and it does so in two layers to avoid false positives. Phrases that explicitly name the extraction itself ("further extraction", "not yet extracted", 「需進一步擷取」) count anywhere in a value, since a real API description never discusses its own extraction. Generic placeholders ("TBD", "to be determined", 「待補」) count only when they are the entire field, because "amount to be determined at capture" is legitimate API prose. ASCII phrases match on word boundaries — CJK has none, so those stay substring matches. Without this check a run could finish as passed with empty artifacts.

Know the scope limit. The scan only recognises well-structured Markdown: headings, GFM tables with a separator row, and fenced code blocks. A source flattened into long single lines — an HTML-to-text dump, for instance — yields zero facts, and the gate is a no-op on it. So a clean gate exit is not by itself evidence of a complete extraction; it only proves nothing contradicted the facts that could be mechanically read. On unstructured sources, keep relying on review.html and human review.

When the message names a line, the cause is already settled. A fence opened there and a later line that looks like its close was refused — most often a closing fence carrying an info string, such as one ending with ```json, which CommonMark reads as opening a new fence rather than closing the old one — so everything after that line went unread. It is reported even when facts before the fence matched the extraction: a source that goes unread halfway through is more dangerous than one never read at all, because the gate appears to have worked. Fix the source and re-extract; the extraction itself needs no change. A fence that simply runs to the end of the document with no refused close is not reported — CommonMark closes an unterminated fence at end of input, so nothing was lost. The reasoning is recorded in docs/adr/0008-an-unclosed-fence-is-reported-not-guessed-shut.md.

That limit is no longer silent. Every assemble records, per manifest source, how many facts were scanned and how many of them matched an extracted endpoint identity, and reports both failure shapes as warning-severity SOURCE_FACTS_UNSCANNED validation issues: zero facts (no endpoint facts were scanned from that source — open it first: content flattened into single lines, or an unconverted PDF/Word file, calls for re-running preprocessing along a table-preserving path such as normalize-html-snapshot or preprocess, and re-reading it achieves nothing; a structurally sound source whose method and path are not on one line — a bare URL with the method on a neighbouring line or stated in prose, or a null-path webhook — will keep the warning permanently, because the scanner never crosses a line to infer a missing method (ADR 0007), and the extraction may be entirely correct; when both are on one line the spelling need not be METHOD /path, since the labelled |URL|<API URL>/Login|Method|GET| form is read too (docs/adr/0011-a-labelled-method-is-a-literal-not-an-inference.md); a prose-only source legitimately lands here) and zero matches (facts were scanned but none matched the extraction by METHOD /path — check whether the extraction missed the endpoints that source documents). The severity is always warning and never blocks a run: a legitimate prose-only source with no parameter tables lands in the zero-fact class, and failing it would read "could not be measured" as "is wrong". It does count against the documentation-quality score under source grounding, so two runs differ in score when one had more sources the gate never judged. verify-extraction forecasts the same thing on stderr, before you pay for plan→generate; the forecast stays out of --json and never changes the exit code. The reasoning is recorded in docs/adr/0007-source-fact-scanning-stays-limited-to-well-structured-markdown.md.

--focus — task-specific extraction focus directives

uv run loop-apidoc verify-extraction --sources ./sources --extraction ./work --focus ./focus.json
uv run loop-apidoc assemble --sources ./sources --extraction ./work --output ./output \
  --source-quality ./work/source-quality --focus ./focus.json --json

Optional on both verify-extraction and assemble; omitting it leaves the pipeline exactly as it was. A focus.json file declares what this particular integration cannot ship without — a settlement callback, a wallet transfer operation, a supplier's error codes. The directives go verbatim into every extraction subagent's prompt, so they really do steer the extraction rather than only audit it afterwards; the extraction agent then answers each one exactly once in <WORK>/focus-response.json. Copyable examples live in the repository's examples/focus/ (payment-integration.focus.json and the matching payment-integration.focus-response.json); there is deliberately no built-in preset flag.

What a focus.json looks like. The file is strict: unknown fields are refused and ids must be unique within it. version is always 1. Each directive requires id (non-blank; the answer refers back by it), kind, intent, and text (non-blank, copied verbatim into every extraction subagent's prompt, so write it as an instruction), plus an optional rationale that records why it matters and travels into the report for the next reader.

{
  "version": 1,
  "directives": [
    {
      "id": "settlement-callback",
      "kind": "expectation",
      "intent": "find_operation",
      "text": "Find the settlement-completed callback endpoint. If no source documents it, list every source you searched.",
      "rationale": "The reconciliation schedule is triggered by this callback."
    },
    {
      "id": "refund-operation",
      "kind": "coverage",
      "intent": "find_operation",
      "text": "Sweep every refund, cancellation, and reversal endpoint. Finding none is not a failure."
    }
  ]
}

What the answer looks like. The extraction agent answers each id exactly once in <WORK>/focus-response.json. reported_by names the endpoint file carrying the anchor, or inventory for a not_found. fragment_digest is the SHA-256 of the normalized source fragment, re-derived from the manifest's bytes rather than trusted.

{
  "version": 1,
  "responses": [
    {
      "id": "settlement-callback",
      "outcome": "satisfied",
      "reported_by": "ep3",
      "anchors": [{
        "type": "operation",
        "value": "POST /v1/callbacks/settlement",
        "evidence": [{
          "version": 1,
          "source": "provider-api.md",
          "locator": {"kind": "line_range", "start_line": 412, "end_line": 412},
          "fragment_digest": "a5a2…5e5d",
          "claim_path": "/summary"
        }]
      }]
    },
    {"id": "refund-operation", "outcome": "not_found", "reported_by": "inventory",
     "searched_sources": ["provider-api.md", "provider-errors.md", "webhooks.md"]}
  ]
}

Read <run-dir>/focus/focus-report.{json,zh-TW.md} after a run. It carries every directive, its anchor resolution, the sources searched, and the outcome. --focus is optional and independent on verify-extraction and assemble, but the answer only reaches this report when assemble is given the file too.

Two kinds of directive, two fields each doing one job. kind is the sole determinant of severity: an expectation asserts that supplier sources document the thing, while a coverage directive only names a scope to sweep, where finding nothing is a complete answer. intent is the sole determinant of anchor type: find_operation, find_field, collect_error_codes. No third field overrides either one — a requester who wants a non-blocking outcome rewrites the directive as coverage instead of adding a downgrade flag.

An answer has exactly two outcomes. satisfied carries anchors, and every anchor must carry a v1 exact evidence reference — a filename alone is refused here, unlike the form the extraction still accepts elsewhere. not_found must list every readable manifest source: the claim being made is "it is in none of them", and one source proves nothing. There is deliberately no "not applicable" outcome — whether a directive applies is the requester's judgement, not the agent's, and that button would be one the agent could always press to get out.

Structural problems and semantic outcomes stay on separate layers. An unanswered directive, an anchor resolving to no extracted endpoint, and evidence naming a source outside the manifest or with a mismatched digest all exit 2 before a run directory is created. An honest not_found passes the gate instead and becomes a FOCUS_UNMET validation issue (error for expectation, warning for coverage), with the run directory and its artifacts written as usual — because the judgement to be made here is "the supplier really does not document it" versus "the search was not thorough enough", and that needs the artifacts and the searched-source list in hand. verify-extraction previews the count of falsified expectations on stderr, but deliberately does not let it affect the exit code.

collect_error_codes carries an additional completeness floor. Where a source presents a well-formed error-code table, its codes become a Documented Error-Code Floor — a deterministic lower bound an exhaustive answer must contain, not a number the requester sets. Reporting fewer codes than the floor produces a FOCUS_INCOMPLETE validation issue naming the omitted codes with the source path and line where each is documented; severity follows kind exactly as it does for FOCUS_UNMET, and the run directory and its artifacts are still written. Reporting more still passes — the floor is a lower bound, never an equality. The floor ignores the directive's own text: collect_error_codes means every code the sources tabulate, and a requester who wants a narrower claim should write an Expectation Directive naming it instead. A source with no recognisable error-code table produces no floor and no judgement. verify-extraction previews the shortfall on stderr the same way, deliberately outside the exit code and outside --json. The reasoning is recorded in docs/adr/0005-the-error-code-floor-comes-from-source-structure-alone.md.

Directives never contaminate the artifacts that are compared across runs. Focus material is written only to <run-dir>/focus/focus-report.{json,zh-TW.md}; provenance.json, the score, and every Foundry-governed asset never see it. Two runs over the same sources with different focus files produce an identical score and byte-identical provenance — otherwise "what the source says" would be contaminated by "who asked what", and a requester could raise a score by writing easier directives. The reasoning is recorded in docs/adr/0004-focus-directives-never-enter-comparable-artifacts.md.

A directive never licenses inventing anything. If the sources do not state it, the answer is not_found, and the run failing validation because of it is the intended outcome — it tells you to get better sources, not a better-sounding answer.

assemble — assemble + validate from the agent-produced extraction JSON

uv run loop-apidoc assemble \
  --sources ./sources \
  --extraction ./work \
  --output ./output \
  [--url <URL> ...] --source-quality ./work/source-quality [--url-coverage <coverage.json>] [--focus ./focus.json] [--extractor-model <model name>] [--architecture-mode legacy|shadow|strict] [--json] [--score]

Required prerequisite: --source-quality must name the passing package produced by assess-sources. Assemble refuses to create an unaudited run, although it cannot prove when an agent read source text outside this process.

Does not extract; it only assembles the extraction directory the agent has already produced (inventory.json + endpoints/*.json, optionally a typed integration.json) into outputs: manifest → plan → generate → validate. The optional contract preserves source-stated transport, amount_direction, idempotency, and line_currency_policy; a missing request currency field never establishes a single-currency policy. If you pass the --source-quality directory produced by assess-sources, assemble rebuilds the manifest and revalidates the embedded source-risk binding before creating a run-dir; a missing, stale, or mismatched audit aborts, while a passing quality report is retained in the run-dir. --url-coverage checks fetch coverage when there are URL sources (warning only). --json prints run_id, run_dir, review_html, ok, status, report, and toolchain to stdout for the agent to parse and drive the correction loop. The run directory also gets a run.json descriptor recording the toolchain (cli_version, extraction_contract_version, skill_version, model) so a run can later be attributed to the versions that produced it; --extractor-model is the extraction model name, passed explicitly by the agent — omit it and the field stays null, because the CLI never guesses it. Exit codes: 0 = validation PASS, 1 = validation FAIL, 2 = extraction input or strict-execution error. Adding --score also writes score/score.{json,md} after assembly (see below); the score does not affect the exit codes above.

--architecture-mode shadow opts into a non-authoritative Core observation after the legacy validation report is written. Success writes source-set, evidence, runtime result, claims, contract, decision, workflow, events, and comparison JSON under <run-dir>/core/; failure writes core/error.json and a warning. Neither result changes legacy validation, score, approval, Foundry, ok/status, or exit codes. The default is legacy and creates no core/.

--architecture-mode strict is the blocking Core-candidate path. It starts only after legacy validation passes and requires exact evidence for every material claim on each legacy-supported plan item. A gap writes core/grounding-report.json and exits 1; an execution error writes core/error.json, marks the run blocked, and exits 2. Success writes an unapproved core/release.json and core/execution.json. Strict never publishes or changes Foundry, and Foundry independently checks its candidate eligibility before any approval.

Shadow evidence is claim-level: each material claim path is connected by explicit_support, derived_support, contradicts, or insufficient to an exact fragment and source artifact. Core uses deterministic value, table-cell, structured-path, enum, and source-fact verification; runtime confidence does not decide status. A prose v1 reference without a parsed scalar can support only its one bound claim after source identity, locator, digest, and claim path all pass. OpenAPI structural derivations are limited to a versioned allowlist and recomputed from the exact fragment plus every required local-reference context fragment. A filename-only or whole-document legacy citation still becomes insufficient and remains unverified. Inspect relationships.json and projections/provenance.json for the claim → relationship → fragment → artifact trace.

validate — validate an existing run directory

uv run loop-apidoc validate --output ./output/<run-id>

Runs the four validation categories — structure / completeness / consistency / no-speculation — over the run directory's outputs, and writes the report into <run-dir>/validation/. Supported/readable sources with zero material citations and successful responses with no usable schema fields appear as warnings. Returns 0 on pass, 1 when there are ERROR-severity issues.

score — grade a completed run directory

uv run loop-apidoc score --output ./output/<run-id> [--profile ci|review] [--min-score N] [--json]

Performs a deterministic documentation-quality score on a completed run directory, computing 0–100 from five weighted categories (openapi_validity / completeness / consistency / source_grounding / reviewability) and reporting response operations, usable schemas, hollow operations, and field count in <run-id>/score/score.{json,md}. --profile sets the score threshold (ci = 85, review = 70), which --min-score can override. Exit codes: 0 = meets threshold, 1 = below, 2 = input file missing or malformed. assemble --score produces the same report as a side effect, but does not affect assemble's exit code (still decided by validation).

evaluate — compare runtime replay results

uv run loop-apidoc evaluate --baseline ./baseline-replay.json --candidate ./candidate-replay.json --output ./evaluation [--json]

Compares two persisted ReplayReport JSON files for the same case and version, writing evaluation-report.{json,md}. It reports candidate-minus-baseline deltas for every quality metric plus cost and latency; missing measurements remain null. This command produces an immutable evaluation artifact only: it never assembles, imports to Foundry, or approves a contract. Exit codes: 0 = complete, 2 = bad input or mismatched case version.

feedback assess — compare passive observations with an approved Normative Contract

uv run loop-apidoc feedback assess \
  --project ./my-api --docset payment --asset <asset-id> \
  --bundle ./feedback-bundle.json --output ./feedback-assessment

Reads one approved Foundry asset and one normalized Observation Bundle, rejects sensitive fields or values before creating the output directory, validates the exact base/contract digests, policy and redaction versions, operation and material-claim paths, replay lineage, attempts, evidence digests, and complete Applicability Envelope, then writes deterministic feedback-assessment.{json,md}. Observation kinds are a semantic allowlist: status/success must bind the same operation's /responses/<status>/status_code, while response field/type must bind a matching /fields/.../name or /fields/.../type in a response-referenced schema; mismatches fail closed. This pure policy lives in core/conformance_policy.py. It performs no network I/O and --output must remain outside .foundry. Exit 0 = closed/no change, 1 = valid discrepancy, inconclusive result, or review subject, 2 = input/integrity/privacy error.

The relationship (confirms, contradicts, inconclusive, or out_of_scope) is an implementation-conformance result, never documentary support. Only confirms/contradicts count as assessed material claims; inconclusive/out-of-scope targets remain untested and open. Deterministic routing is exhaustive: confirmed-only → closed_no_change; other inconclusive → needs_evidence; high-risk contradiction → provider_clarification; harness/fixture failure → implementation_correction; out-of-scope or DNS/proxy/gateway failure → environment_configuration_correction; policy-safe contradiction without documentary evidence → extraction_correction; repeated network/timeout/rate-limit failure → provider_runtime_regression_review; policy-safe grounded contradiction → amendment_proposal.

A reviewed Compatibility Amendment is expiring and exact-scope. An Effective Contract composes one immutable normative release with applicable active amendments and preserves authority lineage per value; the global current remains normative. Conflicts, expiry, drift, open discrepancies, untested material claims, and unresolved_contradiction_count stay visible. “Fully verified” always names the exact envelope, time, suite version, and coverage—never universal 100% truth.

feedback propose — create reviewable amendment proposals

uv run loop-apidoc feedback propose \
  --assessment ./feedback-assessment/feedback-assessment.json \
  --at 2026-08-02T10:00:00+08:00 --output ./feedback-proposals

Reads an assessment and writes amendment-proposals.{json,md} plus one <proposal-id>.json per proposed amendment. Every proposal carries the digest of the complete Normative release—contract plus documentary fragments and support relationships—so later approval fails if any authority-bearing input changed. The timezone-aware --at is required, must not precede the assessment Applicability Envelope's observed_until, and --output must stay outside every .foundry directory. Exit 0 = one or more proposals, 1 = no proposal warranted, 2 = bad input or write failure. This step proposes only; it does not persist a case or publish an Effective Contract.

feedback submit — persist the immutable candidate case stage

uv run loop-apidoc feedback submit \
  --project ./my-api --docset payment \
  --bundle ./feedback-bundle.json \
  --assessment ./feedback-assessment/feedback-assessment.json \
  [--proposal ./feedback-proposals/<proposal-id>.json]

Stores the digest-bound bundle, assessment, optional proposal, and case manifest with explicit status candidate under .foundry/api/docsets/<docset>/feedback/cases/<case-id>/. These inputs are write-once. Before persistence, a deterministic privacy gate rejects sensitive field names and obvious email, phone, national-ID, SSN, passport, and Luhn-valid payment-card values; low-entropy PII must be omitted rather than retained as a hash. No current pointer changes. A case submitted without --proposal remains auditable but cannot be approved. Exit 0 = persisted candidate, 2 = input, integrity, privacy/policy, collision, or I/O failure.

feedback review — record one non-approval decision

uv run loop-apidoc feedback review \
  --project ./my-api --docset payment --case <case-id> \
  --reviewed-by reviewer-001 --reviewer-version 1 \
  --at 2026-08-02T10:30:00+08:00 \
  --disposition needs_evidence --route provider_clarification \
  [--rationale "..."]

Works for an immutable candidate with or without a proposal and records one write-once non-approval decision. The timezone-aware --at and all identity, disposition, and route flags shown above are required. It must not precede observation completion and, when the case has a proposal, must not precede proposal.created_at. --disposition must be rejected or needs_evidence; --route must be one of the deterministic corrective routes and cannot be closed_no_change or amendment_proposal. It revalidates the persisted assessment and all case bindings, applies the same deterministic privacy gate, does not publish an amendment or Effective asset, and cannot replace an existing different decision. Exit 0 = decision recorded (or identical decision already present), 2 = invalid/stale or temporally impossible input, forbidden route/disposition, privacy failure, prior different decision, or I/O failure.

feedback approve — approve an expiring exact-scope amendment

uv run loop-apidoc feedback approve \
  --project ./my-api --docset payment --case <case-id> \
  --approved-by approver-001 --approver-version 1 \
  --at 2026-08-02T10:30:00+08:00 \
  --expires-at 2026-09-02T10:30:00+08:00 \
  [--rationale "..."] [--revalidation-trigger trigger ...] \
  [--supersedes-amendment <amendment-id>]

This is the separate immutable approved-release stage. A named independent human approves the candidate proposal; the producer or runner cannot self-approve. Approval requires timezone-aware decision and expiry timestamps, appends the write-once decision and amendment, derives the Effective Contract, publishes the immutable matching scope-specific Effective asset/current pointer, and leaves global normative current unchanged. --revalidation-trigger may be repeated, but these free-text values are review declarations only; no external trigger-signal contract exists, so they do not schedule automatic execution. Same-target active amendment conflicts fail closed unless --supersedes-amendment explicitly links the same-scope amendment being replaced; prior lineage is then included in composition and recorded. Approval lineage starts with the same bound integrity read used by current: the pointer's effective_asset_digest binds the complete strict-validated canonical EffectiveAsset including all declared fields, so unknown fields fail closed. Every successor pairs supersedes with supersedes_asset_digest to form an immutable hash chain. Governed traversal verifies every predecessor asset digest and amendment artifact digest. A new reviewed amendment may recover expired lineage, but historical asset metadata/amendment/supersession tampering fails before composition and cannot be laundered. Exit 0 = approved Effective release published for that exact scope, 2 = rejected input, independence/integrity/privacy failure, conflict, or I/O failure.

feedback compose — preview exact-target composition without publishing

uv run loop-apidoc feedback compose \
  --project ./my-api --docset payment --asset <asset-id> \
  --target ./target-envelope.json \
  --amendment ./amendment-a.json [--amendment ./amendment-b.json] \
  --at 2026-08-02T10:30:00+08:00 --output ./effective-preview

Deterministically composes one normative release and the active amendments matching the exact target, then writes effective-contract.{json,md} outside .foundry. Composition verifies each amendment against the complete Normative-release digest (contract + documentary fragments + support relationships), not only the projected contract digest. It does not create an asset or current pointer. Exit 0 = no open discrepancy, 1 = composition is valid but still has open discrepancies, 2 = input/integrity/composition failure.

feedback current — resolve the current Effective asset for one exact target

uv run loop-apidoc feedback current \
  --project ./my-api --docset payment --target ./target-envelope.json \
  --at 2026-08-02T11:00:00+08:00

Requires a timezone-aware --at and prints the exact-scope current Effective asset as JSON only while it is effective at that time. Governed models reject unknown fields; lookup accepts only APPROVED and cross-validates Effective Contract identity, applied amendment IDs, validity/counts, approval actor/time, and provenance approval/assessment/bundle bindings. It rejects a query time earlier than approval/composition (not yet effective), an expired release, a release whose base asset is no longer global normative current, and any stale pointer or bounded artifact binding. The pointer's effective_asset_digest verifies the complete strict-validated canonical EffectiveAsset including all declared fields. Asset/pointer records also bind effective-contract.json, compatibility-amendment.json, and provenance.json. Lookup bounds, parses, digest-checks, and cross-checks these bindings. foundry.query is the single read-side I/O for governed lineage traversal, which follows the same supersedes/supersedes_asset_digest hash chain and verifies every predecessor asset and amendment digest. A successful result exposes valid_until, open_discrepancy_count, stale_amendment_count, untested_material_claim_count, and unresolved_contradiction_count. Stale means verifiable release/contract/source/policy/approval-time drift; expiry and inapplicability remain separate. It does not fall back to or replace global normative current. Exit 0 = valid asset resolved, 2 = malformed target/time, not-yet-effective or expired asset, stale base/digest/artifact/lineage, integrity error, or no matching scope-specific pointer.

feedback provider-erratum — prepare a non-mutating normative-pipeline handoff

uv run loop-apidoc feedback provider-erratum \
  --metadata ./provider-erratum.json --artifact ./provider-erratum.pdf \
  --output ./provider-erratum-handoff

Verifies the local metadata/artifact digest binding and writes provider-erratum-handoff.{json,md} outside .foundry. The handoff orders: register supplemental source → acquire/preprocess the immutable readable package → manifest and pre-agent source-risk → agent quality review and assess-sources → extract, verify, and assemble → human review/import/approval of a new Normative release → reassess feedback against that new base. The command does not execute those stages or mutate Foundry. Exit 0 = verified handoff written, 2 = input, digest, path, or write failure.

diff — compare the version difference between two runs

uv run loop-apidoc diff --base ./output/<old-run> --head ./output/<new-run>

Compares two completed run directories, classifying differences by downstream impact into breaking / additive / changed / source_only. By default it writes to <new-run>/diff/report.{json,md}; --output can target another directory. The comparison scope covers openapi.yaml, integration-contract.json, provenance.json, validation/report.json, and manifest.json; the first version does not compare the Markdown guide or generated examples. Exit codes: 0 = complete, 2 = input run-dir missing files or malformed.

foundry — project-local asset governance for an API project

uv run loop-apidoc foundry [init|import|approve|list|current] --help

Manages the project-local .foundry/api/ asset layer: import a completed run as a docset candidate (import), approve it into a versioned, self-contained normative asset (approve), and use deterministic current / list reads. Normative asset.json / current.json use strict, versioned normative-asset/v1 / normative-current/v1 schemas; the pointer binds the complete asset-manifest digest and a deterministic digest for every resolvable artifact. Current reads reject unknown fields, non-APPROVED assets, missing approver lineage, identity/summary drift, absolute/traversal paths, symlinks, escapes, missing targets, and changed bytes. Unbound legacy records have no silent fallback: an operator must run approve --reapprove-legacy --by <operator> --legacy-current-sha256 <trusted-current-digest> --legacy-asset-sha256 <trusted-asset-digest> with a new candidate, using exact raw-byte SHA-256 values from a trusted backup/release inventory; both bindings are checked before parsing, legacy bytes remain untouched, and a new v1 asset is created. The flag accepts only unversioned, summary-consistent heads and rejects v1 or unsupported versions. A new asset records supersedes, and the current pointer advances only after atomic publication; a failed advance restores the prior pointer, docset, and catalog heads for retry. This one global current is always normative; Effective Contract selection is deployment/scope-specific and never replaces it.

review — local comparison, handoff, and human approval

uv run loop-apidoc review --project ./my-api --docset payment --run ./output/<run-id>

Starts a single-user workbench on 127.0.0.1; it automatically imports the completed run when the candidate does not yet exist. It compares with Foundry's current asset, or opens a baseline review for the first version. The page presents validation, version differences, and subjective conclusions. When the candidate includes Core evidence, each matching validation finding and unambiguously matching operation-level version diff exposes its relationship (explicit_support, derived_support, contradicts, or insufficient), fragment locator and digest, and retained source excerpt, with links to the Core review artifacts. Insufficient or contradictory evidence is labelled as such, never presented as support. The workbench then saves conclusions as candidate review/decision.json handoff. Only a human approval updates current. Failed validation, differences, or unresolved handoffs do not lock approval, but the resulting asset is marked needs_follow_up. The workbench never calls a model or replaces deterministic validation.

Validation rules summary

Category Content
Structure OpenAPI 3.1 validity; every endpoint must have a method, a path, and at least one response
Completeness Sources marked unverified, missing required fields, and manifest coverage gaps (unreadable sources, etc.) fail validation
Consistency The endpoint set and security names must agree across OpenAPI, Markdown, and provenance
No speculation Every output item must map to a provenance source; content with no source support is a violation

Validation classifies issues: OPENAPI_INVALID / OUTPUT_MISMATCH → fixable by regeneration; REQUIRED_INFO_MISSING → the agent re-reads the relevant sources to fill the gap; SOURCE_UNVERIFIED / SOURCE_CONFLICT / UNSUPPORTED_ASSERTION → unfixable (fail-closed, reported as a gap/conflict). Correction is agent-driven based on the assemble --json report (re-read sources, overwrite the extraction JSON, then re-run) rather than a loop built into the CLI.

Benchmark quality gate: CI-safe and strict-local

The benchmark harness has four guarantees: committed fixture inventory, discovery guard, source-backed execution, and strict-local preflight. The current 13 refers to unique case directories, not pytest item count; one case feeds several parametrized tests. See docs/BENCHMARK_VALIDATION_PLAN.md for the full contract.

CI-safe operation

uv run python scripts/quality_gate.py

CI-safe mode does not require the operator-provided, gitignored benchmarks/<case>/sources/ snapshots. It runs lint and the full pytest suite, including fixture discovery and exact parity between REQUIRED_BENCHMARK_CASES and committed fixtures. Source-backed case assertions SKIP when their sources are unavailable; this proves that the case is committed and discoverable, not that the benchmark passed.

Sanitized exact-evidence CI lane

uv run python scripts/quality_gate.py --sanitized-fixtures

Exact-evidence or Core-parity changes can use this independent lane to replay the reviewed, line-preserving, redistributable fragments listed in SANITIZED_BENCHMARK_CASES. The current pilot is rsg-game-transfer-wallet. Passing proves fixture-backed exact-evidence parity for retained claims only; it is neither complete source-backed revalidation nor strict-local PASS.

Strict-local operation

uv run python scripts/quality_gate.py --strict-local

Run this only on a machine holding all 13 original, dated source snapshots. The preflight rejects any required sources/ directory that is missing or empty, then runs the source-backed benchmark module. Any pytest skip fails the gate. Passing means required and committed inventories match, every source-backed assertion executed, and the run had zero skips.

--strict-local never accepts sanitized_sources/ as original evidence and cannot be combined with --sanitized-fixtures, preventing the two assurance claims from being confused.

Implementation-backed conformance is a separate lane. Report its exact Applicability Envelope, observation time, suite version, claim coverage, and open discrepancies. It never counts as documentary grounding or a source-backed strict-local pass.

If a historical source cannot be obtained lawfully and reproducibly, record the missing snapshot, complete deterministic CI-safe checks, and perform a legitimate source-backed spot-check for the change. Never substitute newer documentation, synthetic fixtures, or an upstream error page, and never claim strict-local passed.
