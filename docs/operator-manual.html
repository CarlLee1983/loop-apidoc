Loop Engineering 的來源依據式（source-grounded）API 文件 pipeline

English version: README.en.md

loop-apidoc 是一套可重複執行的 CLI，將格式與完整度不一的 API 串接文件，整理成一致、可追溯的標準化產物：

  • OpenAPI 3.1 YAML（openapi.yaml）
  • 繁體中文 Markdown 串接文件（api-guide.zh-TW.md）
  • 離線人工核對頁（review.html）：把缺漏、來源衝突與未確認事項列為可持續追蹤的治理項目；文件未提供 Server URL、authentication details 或 sandbox credentials，不會僅因缺席就被標成整合風險
  • 來源追溯資料（provenance.json）
  • 驗證與缺漏報告（validation/report.{json,md}）

核心原則：供應商來源是 normative、provider-documented claim 的唯一權威。來源未提供的資訊一律不推測；必要資訊缺漏時，驗證會失敗並明確列出缺項，而非以慣例補寫。Implementation conformance 是另一條 empirical、exact-scope 軸。

運作方式

擷取引擎是當前的 coding agent 自己。任何 agent 讀取來源內容前，操作者須先正規化原始二進位輸入、建立 manifest，並通過確定性的 inspect-source-risk 閘。之後 Claude Code plugin 或 OpenAI Codex CLI session 才依 skills/loop-apidoc/SKILL.md 讀取來源、以唯讀 subagent fan-out 擷取(每個 subagent 只讀檔與搜尋、回傳 JSON,不寫檔),主 agent 把結果寫成 inventory.json + endpoints/*.json,再呼叫確定性 CLI assemble 跑後段 plan → generate → validate。

CLI 本身不負責建立 session、登入私有網站或驅動瀏覽器 —— 它只在 agent 寫好擷取 JSON 後做組裝與驗證。

早期曾有以子行程 claude -p 擷取的 run-agent CLI 模式,已於 2026-06 退役(連同 NotebookLM 擷取後端一併移除);現在唯一擷取路徑是 agent-native。

完整流程

URL 導航／快取（可選） → 視需要 preprocess／正規化原始 PDF 或 Word → manifest → inspect-source-risk（必要，agent 讀取前） → assess-sources → 擷取（agent 唯讀 subagent fan-out，可帶 --focus 重點指令） → verify-extraction → assemble manifest → 規格化計畫 → 生成（OpenAPI + Markdown） → 驗證 → 修正（agent 驅動）

驗證失敗時,assemble 以 --json 回報分類後的問題;修正由 agent 自行驅動:依報告回頭重讀相關來源、覆寫對應的擷取 JSON,再重跑 assemble,最多 3 輪。三輪後仍失敗或遇到無法修正的缺漏／衝突,則以缺漏／衝突回報而不補寫。

在 OpenAI Codex CLI 使用

同一份 skill 也能在 Codex 執行。Codex 不會設 ${CLAUDE_PLUGIN_ROOT},因此把 CLI 裝成全域指令,並把 skill 掛進 Codex 的 skills 目錄:

uv tool install --from /path/to/loop-apidoc loop-apidoc

# 2. 把 skill 掛進 Codex（symlink 即可，改檔自動同步）
ln -s /path/to/loop-apidoc/skills/loop-apidoc ~/.codex/skills/loop-apidoc

提供來源

agent 擷取前,操作者只需把來源備妥:

  1. 把本機來源檔案放進一個來源目錄(記為 <SOURCES>)。
  2. 公開 URL 必須先取得成本機 HTML、Markdown 或 OpenAPI snapshot；只有 manifest 綁定且通過 inspect-source-risk 的 artifact 可交給 agent。
  3. 所有原始 PDF／Word 都須先轉成 UTF-8 Markdown；未轉換的 binary document 會 fail closed。

不需建立任何外部 Notebook、不需瀏覽器登入 —— 來源讀取由當前 agent 在 session 內完成。

支援的來源格式

Markdown、HTML、OpenAPI JSON／YAML 可直接掃描；PDF、Microsoft Word（僅 .docx）與公開 URL 必須先轉換或取得成 manifest 綁定的本機可掃描 artifact。舊版二進位 .doc、試算表（.xlsx／.xls）、純文字 .txt 與 .csv 沒有前處理路徑,manifest 會認出格式並直接標成不受支援,並在報告裡指名下一步:.doc 另存為 .docx 或 PDF,試算表把需要的工作表另存為 Markdown 表格,.txt 改副檔名為 .md,.csv 另存為 Markdown 表格,放回 sources/ 後重跑前處理。四者都不會有內建轉檔器——轉檔的判斷留給看得到原始檔案的人,理由見 docs/adr/0012-no-converter-for-legacy-word-or-spreadsheets.md。

取源路徑的證據強度

「這個指令能跑」與「這個指令走過一份真實供應商來源」是兩件事。十三個 benchmark case 的來源只有 .md、.json、.yaml 三種副檔名，所以每條取源路徑照同一把尺標註，而兩個標註不能互換——缺的東西不同，補救方式也不同。

取源路徑證據強度移除標註的條件
manifest、preprocess（PDF）、normalize-html-snapshot來源支撐：有 benchmark case 走過真實供應商來源不適用
import-supplementary-note、import-rendered-url、select-url、related-url-pages、cache-gitbook-llms、.docx 前處理未經真實來源驗證：程式完整、有單元測試，但沒有任何 case 用過它收到第一份走這條路的真實來源，補成 benchmark case
catalog-url、cache-url-pages／cache-url-entry、snapshot-openapi-url、cache-gitbook-llms結構上不進 harness：它們發出網路請求，而 harness 必須離線可重跑一套可重播的錄製機制（把回應存成 fixture 讓 case 離線重跑）

第二類缺的是一份來源，等它到手就能補成 case；第三類缺的是一個機制，再多來源也不會讓網路請求進得了 CI。cache-gitbook-llms 同時列在後兩類，補上真實來源只消掉第二個標註。這張表是寫給人讀的呈現，機器讀的真相是 scripts/quality_gate.py 的 SOURCE_ACQUISITION_EVIDENCE_TIERS——新增一個沒分級的指令，測試就會失敗。import-supplementary-note 值得單獨點名：它的產出會影響驗證報告的 SUPPLEMENTARY_SUPPORT 逐條警告與文件品質分數的 source grounding，是一條會改變分數卻零 case 的路徑。不會為了消掉標註而生一個合成 case。

使用方式

CLI 提供來源處理、URL evidence、草稿擷取、品質與擷取、來源新鮮度、run 處理、Foundry 資產治理，以及 review 本機人工覆核。日常擷取流程仍由 skill 驅動；每個命令都可單獨使用。

preprocess — PDF／DOCX 轉可掃描 markdown

uv run loop-apidoc preprocess --sources ./sources --out ./work/sources_md

PDF 使用 pymupdf4llm；.docx 使用內建 fail-closed OOXML normalizer。受支援的文件會保留標題與表格並輸出 <原檔名>.md；deterministic .source.json sidecar 會記錄 schema／security-policy version、原始與正規化檔名、大小及 SHA-256。政策上限為壓縮檔 25 MiB、2,048 entries、每個 member 10 MiB、解壓總量 50 MiB、壓縮比 100:1。此首個 slice 接受 UTF-8-compatible Transitional OOXML textual DOCX；unsafe ZIP／OPC／XML、巨集與 active DDE field code、markup-compatibility alternate content、外部 relationship、DTD/entity、altChunk、embedded media、有實質內容的 header/footer/note/comment part，以及目前無法忠實輸出的合併儲存格語意，都會在整批輸出前拒絕。既有 Markdown／sidecar、衍生路徑碰撞與 normalization error 一律不覆寫，preprocess 以 exit 2 結束。DOCX ZIP/XML fallback 改編自 MIT 授權的 book-to-skill 固定 revision efda3b2212ce1b2c052126e85e14de40a32442e8；本專案沒有 runtime dependency，也未繼承 EPUB／RTF／MOBI 支援，授權全文見第三方公告。舊式 .doc、試算表、純文字 .txt 與 .csv 維持 passthrough（byte-for-byte 複製，不轉檔），須由操作者用可信任工具轉檔；preprocess 會逐檔印出該格式自己的下一步。之後對精確的 --out 建 manifest、通過 inspect-source-risk，再讓 agent 讀取。

未經真實來源驗證。十三個 benchmark case 沒有任何一個的來源是 Word，tests/ 底下的 DOCX 全部在 tmp_path 裡合成。這條路徑的證據強度等同 benchmark 的 skipped：程式跑得過合成檔，沒有一份真實供應商 Word 交件走過全程。可用但未證實，收到第一份真實交件並補成 benchmark case 時移除此標註。

manifest — 建立來源 manifest

uv run loop-apidoc manifest --sources ./sources-or-file [--url <URL> ...] [--url-coverage <coverage.json>] [--output manifest.json]

掃描本機來源,記錄相對路徑、格式、大小、SHA-256、掃描時間、是否受支援、重複判定與處理狀態;公開 URL 另記錄擷取時間、HTTP 狀態與內容雜湊。--sources 可接受目錄或單一來源檔案；若提供檔案，會以其父目錄作為 sources_root，且 manifest 僅包含該檔案。省略 --output 時輸出至 stdout。

URL 導航與快取 — catalog-url / select-url / cache-url-pages / related-url-pages

# 只下載入口頁一次，建立側欄導航索引（不自動擷取子頁）
uv run loop-apidoc catalog-url --url <入口頁 URL> --output ./work/url_sources/catalog.json

# 依明確範圍選取 catalog 節點（不下載任何 URL）
uv run loop-apidoc select-url --catalog ./work/url_sources/catalog.json --branch <分支> --term <關鍵詞> --output ./work/url_sources/selection.json

# 快取 catalog 全部頁面，建立本機正文／連結／實體索引（不呼叫模型）
uv run loop-apidoc cache-url-pages --catalog ./work/url_sources/catalog.json --output ./work/url_corpus

# 依正文連結與共享實體輸出候選頁卡片；此步驟不授權模型讀取正文
uv run loop-apidoc related-url-pages --corpus ./work/url_corpus/corpus.json --url <頁面 URL> --output ./work/candidates.json

token 節約式的網頁文件讀取流程:catalog.json 是完整導航 coverage universe;corpus.json 不嵌入正文，只指向本機 raw/ 與 body/。candidate card 僅供 routing；任何模型讀取選定頁前，必須先把 raw HTML 或 normalized Markdown materialize 到 <EXTRACT_SOURCES>，重建 manifest 並通過 inspect-source-risk，不得把未 manifest 的 corpus body 交給 agent。catalog 為空或單頁文件時，可用 cache-url-entry；下載的 HTML 可用 normalize-html-snapshot 轉成帶 provenance sidecar 的 Markdown。

import-rendered-url — 匯入受保護的 browser-rendered evidence

uv run loop-apidoc import-rendered-url --input ./captures/page.html --url <原始 URL> \
  --captured-at "2026-07-29T08:30:00+08:00" --capture-method browser_save \
  --sources ./sources --coverage ./work/url_sources/coverage.json [--confirmed-by-user]
uv run loop-apidoc manifest --sources ./sources --url <原始 URL> \
  --url-coverage ./work/url_sources/coverage.json --output ./work/manifest.json

適用於互動式瀏覽器能顯示、但直接 HTTP 取源被擋的頁面。命令保留已儲存的 HTML／Markdown 原始位元組，寫出包含 original/canonical URL、capture time/method、SHA-256 的版本化 provenance，以及 fetched_rendered coverage。既有目的檔、格式錯誤及 URL／path／method／digest mismatch 一律 fail closed；驗證匹配後，manifest 與 assemble 不再探測該受保護 origin。命令不處理 CAPTCHA／credentials、不推論、不 crawl。

import-supplementary-note — 匯入供應商補充說明的人工摘錄

uv run loop-apidoc import-supplementary-note --input ./notes/sandbox-key.md \
  --from "engineer@provider.example" --received-at "2026-08-16T10:00:00+08:00" \
  --subject "測試環境金鑰取得方式" --excerpted-by "carl" --sources ./sources

適用於只存在於信件或通訊軟體訊息裡的規範性資訊——金鑰怎麼取得、測試環境位址、上線前必須完成的事——以及供應商另外給的欄位對照試算表（另存為 Markdown 表格後走同一條路徑）。命令寫出摘錄本身與一份綁定內容的 .source.json sidecar（出處、收到時間、摘錄者、SHA-256），manifest 據此把該來源標成 authority: supplementary；沒有 sidecar 的來源一律是 normative。

次級佐證做得到：被引用、填補 missing、讓一條主張成立。做不到：與正式文件衝突時勝出、在報告裡與正式文件混為一談、支撐 Core 的 explicit_support（shadow／strict 會撤掉它的支撐提案與證據引用）。只靠次級佐證才成立的主張，會在驗證報告裡以 warning 級的 SUPPLEMENTARY_SUPPORT 逐條點名，並計入分數的 source grounding。這類來源也不會進入 record-fingerprint 的指紋——新鮮度比對的前提是來源可被重新取得，而一封信沒有 URL、沒有版本。

要接受的代價：摘錄是人寫的，摘錄者可能寫錯或過度解讀，pipeline 無法分辨。sidecar 記下摘錄者買到的是可追責，不是可驗證。這是唯一帶著這個代價的來源類別，詳見 ADR 0010。sidecar 讀取端 fail closed：缺席才是 normative，讀不動或與內容對不上都會讓 manifest 以 exit 2 拒絕。

snapshot-openapi-url — 固定直連 OpenAPI 來源

uv run loop-apidoc snapshot-openapi-url --url <OpenAPI JSON/YAML URL> \\
  --sources ./sources --coverage ./work/url_sources/coverage.json [--confirmed-by-user]

適用於 URL 已經直接回傳 Swagger 2.0 或 OpenAPI 3.x JSON／YAML 的情況。命令驗證規格宣告後，把原始位元組固定為本機來源，輸出 SHA-256，並寫入 method: direct 的 coverage ledger。既有快照與 coverage 不會被覆寫；後續 manifest 與擷取必須以本機快照為準。

cache-gitbook-llms / extract-markdown-drafts / scaffold-extraction — GitBook Markdown 工程化

uv run loop-apidoc cache-gitbook-llms --url https://example.gitbook.io/docs \\
  --sources ./sources --coverage ./work/url_sources/coverage.json
uv run loop-apidoc manifest --sources ./sources --url https://example.gitbook.io/docs --output ./work/manifest.json
uv run loop-apidoc inspect-source-risk --sources ./sources --manifest ./work/manifest.json --output ./work/source-risk
uv run loop-apidoc extract-markdown-drafts --sources ./sources --manifest ./work/manifest.json --output ./work/markdown-api-facts.json
uv run loop-apidoc scaffold-extraction --sources ./sources --manifest ./work/manifest.json --output ./work/scaffold

此 GitBook 命令只抓一次 llms.txt，快取安全、同網域、入口路徑下的 .md 並保存 sidecar。risk gate 通過前不得檢視 drafts 或重讀 citations。之後 facts／scaffold 仍只供覆核；複製到 workdir、重讀 citations、補齊 gaps 後才執行 verify-extraction。

未經真實來源驗證。十三個 benchmark case 沒有任何一個的來源是 GitBook 站台，這條路徑與 DOCX 一樣可用但未證實，證據強度等同 benchmark 的 skipped。

inspect-source-risk — 確定性的 agent 讀取前來源風險閘

uv run loop-apidoc inspect-source-risk --sources ./sources --manifest ./work/manifest.json \
  --output ./work/source-risk [--max-bytes 5242880]

請在前處理與 manifest 建立後、任何 agent 讀取來源內容前執行。它把 manifest 綁定的 Markdown、HTML、OpenAPI JSON/YAML 當文字掃描，依確定性規則掃描兩個方向：來源會不會操縱 agent（高風險 Unicode、控制字元、instruction／control-token pattern），以及來源會不會洩漏東西給 agent（密鑰與個資）。原始 PDF 與 Word 刻意標為 unscannable 並拒絕通過：須先轉成支援的文字格式，再對精確 bytes 重建 manifest。blocker rules 為 SR-UNICODE-TAG、SR-BIDI-OVERRIDE、SR-CONTROL-CHARACTER、SR-SECRET-VALUE、SR-UNSCANNABLE、SR-SCAN-SIZE-EXCEEDED、SR-INVALID-UTF8、SR-FINDINGS-TRUNCATED；warning rules 為 SR-BIDI-FORMATTING、SR-ZERO-WIDTH-FORMATTING、SR-INSTRUCTION-OVERRIDE-TEXT、SR-CONTROL-TOKEN-TEXT、SR-CREDENTIAL-REFERENCE、SR-CONTACT-PII、SR-PII-VALUE、SR-PAYMENT-CARD、SR-WARNINGS-TRUNCATED。warning 是人工覆核訊號，不是可遵循的來源指令。

洩漏類規則只有自證性材料會擋：SR-SECRET-VALUE 認的是 PEM 私鑰區塊與 JWT，結構本身就是證據。SR-CREDENTIAL-REFERENCE 只給 warning，因為合格的 API 文件本來就會示範 Authorization: Bearer <TOKEN>，而值是真是假無法從文字確定——擋它會拒絕幾乎每一份合格來源，而一個永遠需要 waiver 的閘不是閘。卡號經 Luhn 驗證並排除各卡組織公告的測試卡號。候選只是「長度合格的數字串」，命中是在候選內部沿數字群邊界切窗找出來的——否則同一行左邊緊鄰的編號（1 4539…）會被吃進同一段候選、Luhn 對整串失敗，那筆真卡號一次也不會報。候選不跨行（相鄰兩行數字接起來約十分之一會通過 Luhn），但 NBSP 與全形空格仍算分隔符。

命令輸出 source-risk-report.{json,zh-TW.md}，不改寫來源，也不回顯命中 payload；finding 只含 rule ID、manifest source reference 與 locator。報告最多保留 1,000 筆 finding，其餘命中會用 blocker SR-FINDINGS-TRUNCATED 表示；warning 另有 500 筆的獨立額度，溢出時是 warning 級的 SR-WARNINGS-TRUNCATED——沒有這道分隔，一份合格大型文件裡高頻的聯絡信箱與憑證引用會經由截斷 blocker 把 verdict 變成 reject，而報告裡沒有任何一筆實質命中。blocker 仍可用滿整個上限，所以警告永遠擠不掉真正的命中。退出碼：0 = pass（可含 warning）、1 = reject（blocker 或 unscannable source）、2 = 輸入無效、過期、不安全或不可讀。

assess-sources — 擷取前來源品質閘

uv run loop-apidoc assess-sources --sources ./sources --manifest <manifest.json> \
  --source-risk ./work/source-risk --observations <observations.json> \
  --source-set <名稱> --output ./work/source-quality [--base-manifest <舊 manifest>]

在擷取前依可追溯 observation 評估來源品質,輸出 source-quality-report.{json,zh-TW.md} 與來源差異 source-diff.{json,md},結論為 pass 或 reject。--source-risk 為必要參數：命令會驗證 binding、對目前來源 bytes 重跑確定性檢查，並要求完整 audit 相符後才嵌入 source-quality report。blocker observation 可列出來源明確連結的 required_source_refs；reject report 依原順序去重後輸出為 bounded next-capture seed，絕不自動 crawl。把報告目錄傳給 assemble --source-quality:reject 會在建立 run-dir 前中止組裝;pass 的報告與來源差異會保存進 run-dir 供稽核。

record-fingerprint / check-freshness / check-freshness-batch / governance-scan / governance-review-plan — 來源新鮮度與治理觸發

uv run loop-apidoc record-fingerprint --run-dir ./output/<run-id> --output ./work/source-fingerprint.json [--force]

uv run loop-apidoc check-freshness --fingerprint ./work/source-fingerprint.json \
  [--sources ./sources] [--json] [--report-dir ./work/freshness]

當一份 run 已完成或已核准為 Foundry 資產後,先用 record-fingerprint 從該 run 目錄寫出基準 source-fingerprint.json(本機來源的 SHA-256、每個 URL 來源各抓一次的版本訊號);既有檔案不會被覆寫,除非加上 --force。之後排程(例如 cron)定期執行 check-freshness 即可低成本判斷來源是否值得重新擷取,不需重新解析整份文件也不呼叫模型:OpenAPI URL 來源比較 info.version(版本相同即使位元組不同也視為未變)、HTML 先比對 ETag／Last-Modified 再退回內文 SHA-256、本機檔案比對 SHA-256。退出碼:0=未變(可跳過重新解析)、1=已變(需重跑擷取)、 2=無法判定(有來源抓取或讀取失敗)。加上 --report-dir 時另外寫出 freshness-report.{json,md};未帶則不寫檔。

要一次巡檢多份 docset,改用 check-freshness-batch:

uv run loop-apidoc check-freshness-batch --watchlist ./work/freshness-watchlist.json \
  [--json] [--report-dir ./work/freshness]

freshness-watchlist.json 列出多筆巡檢項目,每筆含 label(識別名稱)、 fingerprint(相對於 watchlist 檔案所在目錄的 source-fingerprint.json 路徑)、選填的 sources(本地來源根目錄,同樣相對於 watchlist 檔案)與選填的 run_dir(僅供顯示)。命令對每一筆逐項執行與 check-freshness相同的比對,單一項目抓取或讀取失敗只會把該項標記為 error 並記錄原因,不會中止整批巡檢;但 watchlist 檔案本身格式錯誤(非合法 JSON 或不符 schema)會直接失敗。彙總退出碼: 0=全部未變、1=有任一已變、2=有任一無法判定或發生錯誤。加上 --report-dir 時另外寫出 freshness-scan.{json,md};未帶則不寫檔。

要把批次結果轉成受控的人工處理觸發，使用 governance-scan：

uv run loop-apidoc governance-scan --watchlist ./work/freshness-watchlist.json \
  [--json] [--report-dir ./work/governance] [--snapshot-dir ./work/governance-snapshot]

來源變動會產生 review_required；無法判定或讀取錯誤則是 attention_required。 命令只會輸出 governance-trigger.{json,md}，不會重新擷取、生成、匯入 Foundry 或核准契約。若提供 --snapshot-dir，同一次掃描中判定為 changed 的原始 bytes 會寫成不可覆寫、內容定址的 evidence pack： sources/<sha256>.source 與 governance-snapshot.json。這避免掃描後重新抓取而造成內容 漂移；unchanged、inconclusive、error 不會被保存，全部未變時也不建立空快照。退出碼： 0=no action、1=review required、2=attention required。

要把觸發轉成 bounded 的人工／agent 交辦，使用 governance-review-plan：

uv run loop-apidoc governance-review-plan --trigger ./work/governance/governance-trigger.json \
  --snapshot ./work/governance-snapshot --output ./work/review-plan [--json]

讀入同一次掃描的 governance-trigger.json；使用快照前會逐一重讀 sources/<sha256>.source 的 bytes、重算 SHA-256 並與 governance-snapshot.json 比對，任一份缺檔或摘要不符即失敗。source_changed 觸發若沒有通過驗證的快照一律拒絕——沒有保存 下來的原始 bytes，就沒有可審的證據。輸出 governance-review-plan.{json,md}，逐個觸發列出 kind、原因、既有 run 目錄、快照來源，以及必要的人工／agent 步驟：來源變動是「審閱保存的 bytes → 另開 工作目錄重新擷取並跑 verify-extraction → assemble、看影響 diff，再要求明確的人工核准」；無法 判定則是「先查清楚來源可用性，在那之前不 assemble、不核准」。命令本身不抓取、不重新擷取、不 assemble、 不匯入 Foundry、不核准契約。退出碼：0=計畫已寫出，2=輸入或快照驗證失敗，或 --output 指到既有檔案。

verify-extraction — 檢查擷取 JSON 是否符合契約

uv run loop-apidoc verify-extraction --sources ./sources --extraction ./work [--url <URL> ...] [--focus ./focus.json]

對 agent 產出的擷取目錄套用與 assemble 相同的輸入閘(schema、來源引用、跨檔不變式、來源事實、延後語句與選填 v1 evidence[])。若提供 exact reference，必須能從 manifest source 依 typed locator 重新 materialize，並吻合 stated normalized-fragment SHA-256；其 claim_path 也必須在 shared normalized-plan projection 中解析成功。命令不寫檔、不建立 run 目錄,適合在組裝前快速驗證擷取 JSON。

來源事實閘會機械掃描 manifest 中的 Markdown 來源,取出端點宣告、參數表與圍籬範例區塊,再以 (METHOD, path) 與擷取結果對照。一旦對上的來源小節寫了欄位或範例、擷取卻交回空的,就 fail closed——靜默遺漏不等於「來源沒寫」。要主張來源沒寫,在 missing 裡具名該欄位即可通過,所以這道閘只會逼出有據可查的缺口,不會逼出捏造。欄位名會沿 schema_ref 遞迴解析進 inventory.schemas,因此把共用 request body 抽成共用型別算去重複,不算遺漏。

另一道檢查攔下佔位式延後答案,並分兩層以避免誤判。明確指涉「擷取這件事」的說法(further extraction、not yet extracted、「需進一步擷取」)出現在值的任何位置都算,因為真實 API 描述不會提到自己的擷取流程;泛用佔位字(TBD、to be determined、「待補」)則只有在整個欄位就只有這句時才算,因為「amount to be determined at capture」是合法的 API 描述。英文片語以詞界比對,CJK 沒有詞界可言,維持子字串比對。少了這道檢查,run 會以 passed 收場而產物是空的。

請注意適用範圍。這道掃描只認得結構良好的 Markdown:標題、含分隔列的 GFM 表格、圍籬程式碼區塊。若來源被壓成一行行超長文字(例如 HTML 轉純文字的傾印檔),掃描結果為零筆事實,這道閘對它就完全沒有作用。因此閘門乾淨通過本身並不等於擷取完整,它只證明「機械讀得到的事實」沒有被違反。面對非結構化來源,仍要靠 review.html 與人工核對。

訊息點名行號時,成因已經確定。那一行開啟的圍籬其後出現過一個「長得像關閉、卻不算關閉」的行(最常見的是關閉行帶了 info string,例如以 ```json 結尾——依 CommonMark 那不算關閉,而是又開了一個新圍籬),因此該行之後的內容完全沒有被讀到。即使前半有事實對上 extraction 也照樣回報:讀到一半才失效比全篇未讀更危險,因為閘門看起來運作正常。修好來源再重新擷取即可,不必動 extraction。圍籬單純沒有收尾、其後沒有疑似關閉行的文件不在此列——CommonMark 在檔尾關閉未終止的圍籬,那種文件沒有任何內容因此遺失。理由記在 docs/adr/0008-an-unclosed-fence-is-reported-not-guessed-shut.md。

這個限制不再是靜默的。每次 assemble 都會逐份 manifest 來源記下「掃出幾筆事實、其中幾筆對得上擷取的端點識別」,並把兩種失能寫成 warning 級的 SOURCE_FACTS_UNSCANNED 驗證問題:零事實(這份來源掃不出任何端點事實。先看它屬於哪一種:內容被壓平成單行、或未轉換的 PDF/Word,補救方向是改走保留表格結構的前處理路徑,例如 normalize-html-snapshot 或 preprocess,重讀來源沒有用;結構完好但 method 與 path 不在同一行(只給完整 URL、method 另起一行或寫在散文裡,或本來就是 path 為 null 的 webhook),掃描器不會跨行去湊那個 method——那是 ADR 0007 拒絕的推論,因此這筆警告會長期存在,擷取本身可能完全正確。反過來說,只要 method 與 path 都寫在同一行,寫法不必是 METHOD /path:帶標籤的 |URL|<API URL>/Login|Method|GET| 同樣認得,理由記在 docs/adr/0011-a-labelled-method-is-a-literal-not-an-inference.md;純散文來源則本來就會落在這裡)與零匹配(掃出了事實,但沒有一筆能以 METHOD /path 對上擷取,補救方向是檢查擷取是否漏了這份來源記載的端點)。severity 恆為 warning、不阻擋 run——純散文、本來就沒有參數表的合法來源會落在零事實這一類,擋下它等於把「量不到」誤判成「錯」——但會計入文件品質分數的 source grounding 類別,讓兩次 run 的分差能表達「這次有更多來源沒被檢查」。verify-extraction 會在 stderr 預告同一件事,讓你在付出 plan→generate 成本之前就能改用別的前處理指令;預告不進 --json、不改退出碼。理由記在 docs/adr/0007-source-fact-scanning-stays-limited-to-well-structured-markdown.md。

--focus — 依任務對擷取下重點指令

uv run loop-apidoc verify-extraction --sources ./sources --extraction ./work --focus ./focus.json
uv run loop-apidoc assemble --sources ./sources --extraction ./work --output ./output \
  --source-quality ./work/source-quality --focus ./focus.json --json

verify-extraction 與 assemble 皆可選用;不給就與現況完全相同。focus.json 裡寫的是「這次串接少了它就不能上線」的東西——金流的結算回呼、遊戲平台的錢包轉帳端點、供應商的錯誤碼。指令會逐字進入每個擷取 subagent 的 prompt,所以它真的導引擷取,不只是事後稽核;擷取 agent 則對每一條恰好應答一次,寫進 <WORK>/focus-response.json。可複製的範本在 repo 的 examples/focus/(payment-integration.focus.json 與對應的 payment-integration.focus-response.json)。

focus.json 長這樣。檔案是嚴格契約:多寫欄位會被拒絕,id 在同一份檔案內必須唯一。version 固定為 1;每條指令必填 id(非空白,應答靠它回指)、kind、intent、text(非空白,會逐字進入每個擷取 subagent 的 prompt,所以要當成指令來寫),選填 rationale 說明為什麼重要、並帶進報告給下一個讀的人。

{
  "version": 1,
  "directives": [
    {
      "id": "settlement-callback",
      "kind": "expectation",
      "intent": "find_operation",
      "text": "一定要找到結算完成的回呼通知端點。若來源真的沒有記載,請列出已查過的每一份來源。",
      "rationale": "對帳排程以此回呼為觸發點,缺了它整份契約無法上線。"
    },
    {
      "id": "refund-operation",
      "kind": "coverage",
      "intent": "find_operation",
      "text": "掃過所有與退款、取消、沖正相關的端點;找不到不算失敗。"
    }
  ]
}

應答長這樣。擷取 agent 對每個 id 恰好應答一次,寫進 <WORK>/focus-response.json。reported_by 指出承載錨點的端點檔,not_found 時為 inventory。fragment_digest 是正規化來源片段的 SHA-256,由 manifest 的 bytes 重新推導比對,不是照單全收。

{
  "version": 1,
  "responses": [
    {
      "id": "settlement-callback",
      "outcome": "satisfied",
      "reported_by": "ep3",
      "anchors": [{
        "type": "operation",
        "value": "POST /v1/callbacks/settlement",
        "evidence": [{
          "version": 1,
          "source": "provider-api.md",
          "locator": {"kind": "line_range", "start_line": 412, "end_line": 412},
          "fragment_digest": "a5a2…5e5d",
          "claim_path": "/summary"
        }]
      }]
    },
    {"id": "refund-operation", "outcome": "not_found", "reported_by": "inventory",
     "searched_sources": ["provider-api.md", "provider-errors.md", "webhooks.md"]}
  ]
}

跑完要讀的是 <run-dir>/focus/focus-report.{json,zh-TW.md}。每條指令、錨點怎麼解析、查了哪些來源、結局是什麼都在裡面。--focus 在 verify-extraction 與 assemble 各自可選、互不依賴,但要讓應答進到這份報告,assemble 那次一定要帶。

兩種指令,兩個欄位各管一件事。kind 是 severity 的唯一來源:expectation 斷言供應商來源確實記載了它,coverage 只指定一個要掃乾淨的範圍、查無記載也算完整回答。intent 是錨點型別的唯一來源:find_operation、find_field、collect_error_codes。沒有第三個欄位可以覆寫任何一個——想要不阻斷的結局,把指令改寫成 coverage,而不是加降級旗標。

應答只有兩種結局。satisfied 帶錨點,每個錨點必須附 v1 exact evidence——只給檔名會被拒絕,而那是擷取其他地方仍然接受的形式。not_found 必須列出 manifest 中每一份可讀來源:宣稱的是「它不在任何一份裡」,列一份證明不了那件事。刻意沒有「不適用」這個結局——一條指令適不適用是提出者的判斷,給 agent 那顆按鈕等於給它一個永遠能按的脫身鍵。

結構問題與語意結局分兩層。沒人應答的指令、指不到任何已擷取端點的錨點、指向 manifest 以外或 digest 不符的證據,都在建立 run 目錄之前以 2 結束。誠實的 not_found 則通過閘門,成為 FOCUS_UNMET 驗證問題(expectation 為 error、coverage 為 warning),run 目錄與產物照常寫出——因為此時要判斷的是「供應商真的沒寫,還是查得不夠」,而那需要產物與已查來源清單一起在手上。verify-extraction 會在 stderr 預告落空的斷言數量,但刻意不影響退出碼。

collect_error_codes 另外有一道下界判準。來源只要以結構良好的表格列出錯誤碼,那些碼就構成「記載錯誤碼下界」(Documented Error-Code Floor)——用來判斷答案是否窮盡的機械下界,而非提出者自訂的數字。回報的碼比下界少,產生 FOCUS_INCOMPLETE 驗證問題,具名列出漏掉的碼與其記載的來源路徑、行號,severity 同樣只看 kind,run 目錄與產物照常寫出;回報得比下界多仍然通過,下界是下界不是相等。下界不理會指令 text 寫的範圍——collect_error_codes 就是要供應商全部的錯誤碼,想要窄範圍的斷言,改寫 Expectation Directive 具名指定。來源辨認不出錯誤碼表格,就沒有下界、也不下判斷。verify-extraction 同樣會在 stderr 預告落差,一樣刻意不影響退出碼、不出現在 --json 裡。理由記在 docs/adr/0005-the-error-code-floor-comes-from-source-structure-alone.md。

指令不會污染跨 run 可比的產物。focus 材料只寫進 <run-dir>/focus/focus-report.{json,zh-TW.md};provenance.json、score 與所有 Foundry 治理資產都看不到它。同一份來源、不同 focus 的兩次 run,分數相同、provenance 逐位元組相同——否則「來源說了什麼」會被「誰問了什麼」污染,而提出者還能靠寫寬鬆的指令把分數拉高。理由記在 docs/adr/0004-focus-directives-never-enter-comparable-artifacts.md。

指令從不授權捏造。來源沒寫就是 not_found,run 因此驗證失敗正是預期結果——它告訴你該補的是來源,不是換一個聽起來比較好的答案。

assemble — 從 agent 產出的擷取 JSON 組裝 + 驗證

uv run loop-apidoc assemble \
  --sources ./sources \
  --extraction ./work \
  --output ./output \
  [--url <URL> ...] --source-quality ./work/source-quality [--url-coverage <coverage.json>] [--focus ./focus.json] [--extractor-model <模型名稱>] [--architecture-mode legacy|shadow|strict] [--json] [--score]

必要前置條件：--source-quality 必須指定 assess-sources 產出的 pass 套件。assemble 會拒絕建立未稽核 run，但無法證明本流程外 agent 讀取來源文字的時間順序。

不擷取,只把 agent 已產出的擷取目錄(inventory.json + endpoints/*.json,選用 typed integration.json)組裝成輸出:manifest → plan → generate → validate。選填契約保存來源明載的 transport、amount_direction、idempotency 與 line_currency_policy；request 沒有 currency 欄位不會被當成單幣別證據。若傳入 assess-sources 產出的 --source-quality 目錄，assemble 會重建 manifest，並在建立 run-dir 前重新驗證內嵌 source-risk binding；audit 缺失、過期或不匹配會中止，通過的 quality report 才保存進 run-dir。--url-coverage 在有 URL 來源時檢核撈取涵蓋率(僅 warning)。--json 會把 run_id、run_dir、review_html、ok、status、report、toolchain 印到 stdout,供 agent 解析並驅動修正迴圈。run 目錄另寫出 run.json,記錄 toolchain(cli_version、extraction_contract_version、skill_version、model)以便日後歸因;--extractor-model 由 agent 明確帶入擷取模型名稱,省略即 null(CLI 不推測)。退出碼:0=驗證 PASS、1=驗證 FAIL、2=擷取輸入檔或 strict 執行錯誤。加上 --score 會在組裝後一併寫出 score/score.{json,md}(見下),評分不影響上述退出碼。

--architecture-mode shadow 會在 legacy validation report 寫出後啟用非權威的 Core 觀測旁路。成功時將 source-set、evidence、runtime result、claims、contract、decision、workflow、events 與 comparison JSON 寫入 <run-dir>/core/；失敗時寫出 core/error.json 並顯示 warning。兩者都不改變 legacy validation、score、approval、Foundry、ok/status 或退出碼。預設為 legacy，不建立 core/。

--architecture-mode strict 是阻斷式 Core candidate 路徑。它只在 legacy validation 通過後執行，並要求每個 legacy-supported plan item 的所有 material claim 都有 exact evidence。缺口會寫出 core/grounding-report.json 並以 1 結束；執行錯誤會寫出 core/error.json、run 標記為 blocked 並以 2 結束。成功會寫入未核准的 core/release.json 與 core/execution.json。strict 不會發布或改動 Foundry，且 Foundry 會在人工核准前獨立驗證 candidate eligibility。

Shadow evidence 提升為 claim-level：每個 material claim path 透過 explicit_support、derived_support、contradicts 或 insufficient 連到 exact fragment 與 source artifact。Core 使用確定性的值、table cell、structured path、enum 與 source-fact verification；runtime confidence 不決定 status。沒有 parsed scalar 的 prose v1 reference 只有在 source identity、locator、digest 與 claim path 全部通過時，才能支援它綁定的單一 claim。OpenAPI structural derivation 限 versioned allowlist，並會從 exact fragment 與所有必要的 local-reference context fragments 重新計算。只有檔名或整份文件的 legacy citation 仍會成為 insufficient 並維持 unverified。請從 relationships.json 與 projections/provenance.json 檢查 claim → relationship → fragment → artifact 追蹤鏈。

validate — 驗證既有 run 目錄

uv run loop-apidoc validate --output ./output/<run-id>

對 run 目錄輸出執行結構／完整性／一致性／禁止推測四類驗證,並將報告寫入 <run-dir>/validation/。supported/readable 但零實質引用的來源，以及成功 response 沒有可用 schema 欄位，會以 warning 浮現；通過回傳 0,有 ERROR 級問題回傳 1。

score — 為完成的 run 目錄評分

對已完成 run directory 做確定性文件品質評分,五類加權(openapi_validity／completeness／consistency／source_grounding／reviewability)算出 0–100，並列出 response operation、可用 schema、空殼 operation 與欄位總數，寫入 <run-id>/score/score.{json,md}。--profile 決定分數門檻(ci=85、review=70),可用 --min-score 覆寫。退出碼:0=達門檻、1=未達、2=輸入缺檔或格式錯誤。assemble --score 會附帶產生同一份報告,但不影響 assemble 的退出碼(仍由 validation 決定)。

evaluate — 比較 runtime replay 結果

uv run loop-apidoc evaluate --baseline ./baseline-replay.json --candidate ./candidate-replay.json --output ./evaluation [--json]

比較同一案例與版本的兩份已保存 ReplayReport JSON，輸出 evaluation-report.{json,md}。報告列出每個品質 metric 的 candidate-minus-baseline delta 與 cost／latency delta；缺少量測值會保留 null。此命令只產生 immutable evaluation artifact，不會 assemble、匯入 Foundry 或核准契約。退出碼：0=完成、2=輸入錯誤或案例版本不一致。

feedback assess — 把被動 observation 與已核准 Normative Contract 比對

uv run loop-apidoc feedback assess \
  --project ./my-api --docset payment --asset <asset-id> \
  --bundle ./feedback-bundle.json --output ./feedback-assessment

讀取一個已核准 Foundry asset 與一份 normalized Observation Bundle，在建立輸出目錄前拒絕敏感欄位或值，驗證精確 base／contract digest、policy／redaction version、operation／material-claim path、replay lineage、attempt、evidence digest 與完整 Applicability Envelope，再寫出 deterministic feedback-assessment.{json,md}。Observation kind 是語意 allowlist：status／success 必須綁定同一 operation 的 /responses/<status>/status_code；response field／type 必須綁定 response 所引用 schema 中相符的 /fields/.../name 或 /fields/.../type，不符即 fail closed；pure policy 位於 core/conformance_policy.py。命令不做 network I/O，且 --output 必須位於 .foundry 之外。退出碼：0=closed／無需變更、1=有效 discrepancy、inconclusive 或 review subject、2=input／integrity／privacy error。

confirms、contradicts、inconclusive、out_of_scope 是 implementation-conformance relationship，永遠不是 documentary support。只有 confirms／contradicts 計入 assessed material claim；inconclusive／out-of-scope target 仍是 untested 且 open。八條 deterministic route 全部可達：全數確認 → closed_no_change；其他 inconclusive → needs_evidence；高風險 contradiction → provider_clarification；harness／fixture failure → implementation_correction；out-of-scope 或 DNS／proxy／gateway failure → environment_configuration_correction；沒有 documentary evidence 的安全 contradiction → extraction_correction；重複 network／timeout／rate-limit failure → provider_runtime_regression_review；有 documentary grounding 的安全 contradiction → amendment_proposal。

經審查的 Compatibility Amendment 有期限且綁定 exact scope；Effective Contract 把一個不可變 normative release 與適用 active amendments 組合，每個值保留 authority lineage，而全域 current 仍保持 normative。衝突、expiry、drift、open discrepancy、未測 material claim 與 unresolved_contradiction_count 都要保留。「Fully verified」必須具名 exact envelope、時間、suite version 與 coverage，不能宣稱普遍 100% 真實。

feedback propose — 產生可審查的 amendment proposals

uv run loop-apidoc feedback propose \
  --assessment ./feedback-assessment/feedback-assessment.json \
  --at 2026-08-02T10:00:00+08:00 --output ./feedback-proposals

讀取 assessment，寫出 amendment-proposals.{json,md}，並為每個提案寫一份 <proposal-id>.json。每個 proposal 都攜帶完整 Normative release digest——contract 加上 documentary fragments 與 support relationships——因此任何具 authority 的 input 改變，後續 approval 都會失敗。必須提供含時區的 --at，且不得早於 assessment Applicability Envelope 的 observed_until；--output 不得位於任何 .foundry 內。退出碼：0＝產生至少一份提案、1＝沒有合理提案、2＝輸入或寫入錯誤。這一步只提案，不保存 case，也不發布 Effective Contract。

feedback submit — 保存 immutable candidate case stage

uv run loop-apidoc feedback submit \
  --project ./my-api --docset payment \
  --bundle ./feedback-bundle.json \
  --assessment ./feedback-assessment/feedback-assessment.json \
  [--proposal ./feedback-proposals/<proposal-id>.json]

把 digest-bound bundle、assessment、選用 proposal 與 case manifest 以明確的 candidate status 保存至 .foundry/api/docsets/<docset>/feedback/cases/<case-id>/；這些 inputs 為 write-once。持久化前，deterministic privacy gate 會拒絕敏感欄位名稱，以及明顯 email／phone／national-ID／SSN／passport／Luhn-valid payment-card 值；低 entropy PII 必須省略，不得改以 hash 保留。命令不會改動任何 current pointer。沒有 --proposal 的 case 仍可稽核，但不能 approve。退出碼：0＝candidate 保存成功、2＝輸入、完整性、privacy／政策、碰撞或 I/O 錯誤。

feedback review — 寫入一次 non-approval decision

uv run loop-apidoc feedback review \
  --project ./my-api --docset payment --case <case-id> \
  --reviewed-by reviewer-001 --reviewer-version 1 \
  --at 2026-08-02T10:30:00+08:00 \
  --disposition needs_evidence --route provider_clarification \
  [--rationale "..."]

可處理有或無 proposal 的 immutable candidate，並記錄一次 write-once non-approval decision。上列 identity、含時區的 --at、disposition 與 route 都必填。決策時間不得早於 observation completion；若 case 有 proposal，也不得早於 proposal.created_at。--disposition 只能是 rejected 或 needs_evidence；--route 必須是 deterministic corrective route，且不得為 closed_no_change 或 amendment_proposal。命令會重驗 persisted assessment 與所有 case binding、套用相同 deterministic privacy gate，不會發布 amendment／Effective asset，也不能覆蓋既有的不同 decision。退出碼：0＝decision 已寫入（或完全相同的 decision 已存在）、2＝輸入／binding stale 或時間順序不可能、route／disposition 禁止、privacy 失敗、已存在不同 decision 或 I/O 錯誤。

feedback approve — 核准有期限的 exact-scope amendment

uv run loop-apidoc feedback approve \
  --project ./my-api --docset payment --case <case-id> \
  --approved-by approver-001 --approver-version 1 \
  --at 2026-08-02T10:30:00+08:00 \
  --expires-at 2026-09-02T10:30:00+08:00 \
  [--rationale "..."] [--revalidation-trigger trigger ...] \
  [--supersedes-amendment <amendment-id>]

這是分開的 immutable approved-release stage。由具名且獨立的人工核准 candidate proposal；producer 或 runner 不能 self-approve。核准需要含時區的決策與 expiry timestamp；附加 write-once decision 與 amendment，接著衍生 Effective Contract，發布 immutable 且相符 scope-specific Effective asset／current pointer，而全域 normative current 維持不變。--revalidation-trigger 可重複傳入，但自由文字只是 review declaration；目前沒有外部 trigger-signal contract，因此不會排程自動執行。同 target 的 active amendment 衝突會 fail closed；只有 --supersedes-amendment 明確連結同 scope 被取代 amendment 時，才會把既有 lineage 納入 composition 並記錄。Approval lineage 從與 current 共用的 bound integrity read 開始：pointer 的 effective_asset_digest 綁定包含所有宣告欄位、經 strict validation 後的 canonical EffectiveAsset；未知欄位 fail closed。每個 successor 以成對的 supersedes／supersedes_asset_digest 形成 immutable hash chain。Governed traversal 逐節驗證 predecessor asset digest 與 amendment artifact digest。新的 reviewed amendment 可恢復 expired lineage，但任何歷史 asset metadata／amendment／supersession 竄改都在 composition 前 fail closed，不能藉 lineage 洗白。退出碼：0＝approved Effective release 已發布至該 exact scope、2＝輸入拒絕、獨立性／完整性／privacy 失敗、衝突或 I/O 錯誤。

feedback compose — 預覽 exact-target 組合但不發布

uv run loop-apidoc feedback compose \
  --project ./my-api --docset payment --asset <asset-id> \
  --target ./target-envelope.json \
  --amendment ./amendment-a.json [--amendment ./amendment-b.json] \
  --at 2026-08-02T10:30:00+08:00 --output ./effective-preview

確定性組合一份 normative release 與符合 exact target 的 active amendments，並在 .foundry 外寫出 effective-contract.{json,md}。Composition 會用完整 Normative-release digest（contract + documentary fragments + support relationships）驗證每個 amendment，而非只綁 projected contract digest。它不建立 asset 或 current pointer。退出碼：0＝沒有 open discrepancy、1＝組合有效但仍有 open discrepancies、2＝輸入、完整性或組合失敗。

feedback current — 解析一個精確 target 的 current Effective asset

uv run loop-apidoc feedback current \
  --project ./my-api --docset payment --target ./target-envelope.json \
  --at 2026-08-02T11:00:00+08:00

必須提供含時區的 --at，而且只有 Effective asset 在該時間已生效且仍有效時才會以 JSON 印出。Governed models 拒絕未知欄位；lookup 只接受 APPROVED，並 cross-validate Effective Contract identity、applied amendment IDs、validity／counts、approval actor／time 與 provenance approval／assessment／bundle bindings。Query time 早於 approval／composition（not yet effective）、已過期、base asset 已不是全域 normative current，或 pointer／bounded artifact binding stale 時都會拒絕。Pointer 的 effective_asset_digest 驗證包含所有宣告欄位、經 strict validation 後的 canonical EffectiveAsset；asset／pointer 也綁定 effective-contract.json、compatibility-amendment.json、provenance.json。foundry.query 是 governed lineage traversal 唯一 read-side I/O，會沿 supersedes／supersedes_asset_digest hash chain 逐節驗證 predecessor asset 與 amendment digest。成功結果揭露 valid_until、open_discrepancy_count、stale_amendment_count、untested_material_claim_count、unresolved_contradiction_count；stale 只指可驗證的 release／contract／source／policy／approval-time drift，expiry 與 inapplicable 分開。不會 fallback 至全域 normative current，也不會取代它。退出碼：0＝解析出有效 asset、2＝target／time 格式錯誤、not-yet-effective／expiry、stale base／digest／artifact／lineage、完整性錯誤或沒有相符 scope-specific pointer。

feedback provider-erratum — 準備不改動治理狀態的 normative-pipeline handoff

uv run loop-apidoc feedback provider-erratum \
  --metadata ./provider-erratum.json --artifact ./provider-erratum.pdf \
  --output ./provider-erratum-handoff

驗證本機 metadata／artifact digest binding，並在 .foundry 外寫出 provider-erratum-handoff.{json,md}。handoff 依序要求：登記 supplemental source → 取得／前處理 immutable readable package → manifest 與 agent 讀取前 source-risk → agent 品質審查及 assess-sources → extract、verify、assemble → 人工 review／import／approve 新 Normative release → 以新 base 重做 feedback assessment。命令本身不執行這些階段，也不改動 Foundry。退出碼：0＝已驗證並寫出 handoff、2＝輸入、digest、路徑或寫入失敗。

diff — 比較兩次 run 的版本差異

foundry — API 專案本地資產治理

uv run loop-apidoc foundry [init|import|approve|list|current] --help

管理專案本地 .foundry/api/ 資產層：把完成的 run 匯入為 docset candidate（import），核准為版本化、自足複本的 normative asset（approve），並以確定性的 current／list 讀取。Normative asset.json／current.json 使用 strict、versioned normative-asset/v1／normative-current/v1 schemas；pointer 綁定完整 asset manifest digest 與每個可解析 artifact 的 deterministic digest，current query 會拒絕未知欄位、非 APPROVED、缺少 approver lineage、identity／summary drift、absolute／traversal／symlink／越界路徑、缺失 target 或 bytes 竄改。未綁定舊格式不會 silent fallback；operator 必須帶新 candidate 明確執行 approve --reapprove-legacy --by <operator> --legacy-current-sha256 <trusted-current-digest> --legacy-asset-sha256 <trusted-asset-digest>，並使用 trusted backup／release inventory 的 exact raw-byte SHA-256；兩份 binding 會在 parsing 前比對，legacy bytes 不改寫且建立新的 v1 asset。flag 只接受未版本化、summary 一致的 head，v1／未知版本會拒絕。新 asset 記錄 supersedes，成功發布後 current pointer 才以 atomic write-new-then-advance 前進；推進失敗會恢復舊 pointer、docset 與 catalog head，供 retry。這個唯一全域 current 永遠保持 normative；Effective Contract selection 綁定 deployment／scope，不會取代它。

review — 本機比對、交棒與人工核准

uv run loop-apidoc review --project ./my-api --docset payment --run ./output/<run-id>

在 127.0.0.1 啟動單使用者工作台；若 candidate 尚未存在，會自動匯入完成的 run。它與 Foundry 的 current 比對，第一版則建立 baseline review；畫面顯示驗證結果、版本差異與可交棒的主觀結論。若 candidate 包含 Core evidence，對應的 validation finding，以及能明確對應的 operation-level version diff，會顯示 relationship（explicit_support、derived_support、contradicts 或 insufficient）、fragment locator／digest 與保留的來源 excerpt，並連到 Core review artifacts。不足或矛盾證據會明確標示，不會被呈現為支持。結論會寫成 candidate 的 review/decision.json。只有人工點選核准才更新 current。驗證失敗、差異或未處理 handoff 不會鎖死核准，但正式資產會標記為 needs_follow_up。工作台不呼叫模型，也不取代確定性驗證。

驗證規則摘要

類別 內容
結構 OpenAPI 3.1 合法性;endpoint 必須有 method、path 與至少一個 response
完整性 標記 unverified 的來源、缺漏必要欄位、manifest 涵蓋缺口(不可讀來源等)會使驗證失敗

Benchmark 品質閘：CI-safe 與 strict-local

Benchmark harness 有四層保證：已提交 fixture 清單、discovery 守門、來源支撐執行、strict-local 預檢。目前的 13 是唯一 case 目錄數，不是 pytest test item 數；同一 case 會供多個參數化測試使用。完整 contract 見 docs/BENCHMARK_VALIDATION_PLAN.md。

CI-safe 操作

Sanitized exact-evidence CI lane

uv run python scripts/quality_gate.py --sanitized-fixtures

exact-evidence 或 Core parity 變更可用這條獨立 lane，重播 SANITIZED_BENCHMARK_CASES 明列、經審核且保留原始行號的可重新散布片段。目前 pilot 是 rsg-game-transfer-wallet。通過只代表 retained claims 的 fixture-backed exact-evidence parity；不是完整 source-backed 重驗，也不能稱為 strict-local PASS。

Strict-local 操作

uv run python scripts/quality_gate.py --strict-local

只在同一台機器持有全部 13 份原始、具日期的來源快照時執行。預檢會先拒絕任何缺少或內容為空的 required sources/，再跑 source-backed benchmark module；只要 pytest 回報任一 skip，整個 quality gate 就失敗。通過表示 required/committed 完全一致、所有來源支撐斷言都實際執行，且零 skip。

--strict-local 不會接受 sanitized_sources/ 當原始來源，且不能和 --sanitized-fixtures 合併執行，避免混淆兩種 assurance。

Implementation-backed conformance 是獨立 lane。必須回報精確 Applicability Envelope、observation time、suite version、claim coverage 與 open discrepancy；它不能算 documentary grounding，也不能算 source-backed strict-local pass。

若歷史來源無法合法或可重現地取得，請記錄缺少的快照，完成確定性 CI-safe 檢查，並對本次改動做合法的來源支撐 spot-check。不得用新版文件、合成 fixture 或 upstream error page 代替歷史證據，也不得宣稱 strict-local passed。

loop_apidoc/feedback/ 涵蓋八條 deterministic route 的被動 normalized-JSON assessment／proposal／composition、治理 submit／write-once non-approval review／approval adapters、驗證三份 digest-bound artifacts 並揭露 open／untested／unresolved counters 的 timezone-aware exact-target Effective 查詢，以及 Provider Erratum handoff；dry-run 輸出位於 .foundry 外，治理寫入透過 Foundry，所有命令都不做 provider network I/O
loop_apidoc/extraction/ agent 擷取共用的 models 與工具(models、stages、questions、store、jsonblock)
loop_apidoc/plan/ 規格化計畫建構與來源比對分類
loop_apidoc/generate/ OpenAPI / Markdown / review.html / provenance / examples / handoff 生成(檔案 I/O 出口之一)
loop_apidoc/validate/ 結構／完整性／一致性／禁止推測驗證、零引用來源與空殼 response 告警
loop_apidoc/run/ run-id 產生、結果／狀態 models、將計畫寫入 run 目錄
loop_apidoc/diff/ run 對 run 版本差異:讀取產物、分類差異(breaking／additive／changed／source_only)、輸出 diff/report.{json,md}
loop_apidoc/preparation/ 產生前就緒度評估,於 assemble 內把 manifest／inventory／endpoints／plan 評成 preparation-report.{json,md}(檔案 I/O 出口之一)
loop_apidoc/score/ 對完成 run-dir 做確定性文件品質評分,五類加權算出 0–100,輸出 score/score.{json,md}(檔案 I/O 出口之一)
loop_apidoc/source_risk/ 以 manifest 綁定、在 agent 讀取前執行的文字風險掃描與報告驗證(inspect-source-risk)；讀取精確來源 bytes 並寫出稽核，但不改寫來源或回顯 payload
loop_apidoc/source_quality/ 擷取前來源品質評估與來源版本差異報告(assess-sources)；要求並嵌入已驗證的 source-risk audit，pass 報告可隨 run-dir 保存
loop_apidoc/freshness/ 來源新鮮度排程閘(record-fingerprint／check-freshness／check-freshness-batch):基準 fingerprint 寫出與比對,退出碼 0/1/2 判斷是否需重新擷取,選填 freshness-report.{json,md};check-freshness-batch 對 watchlist 逐項比對後彙總為 freshness-scan.{json,md}(檔案 I/O 出口之一)
loop_apidoc/url_catalog.py / url_corpus.py 受限 URL 導航索引、頁面快取與關聯候選(catalog-url／select-url／cache-url-pages／cache-url-entry／normalize-html-snapshot／related-url-pages),讓 agent 以本機證據讀取網頁文件。導航解析會略過純 UI 控制項(無目標的錨點、role="button"、下拉開關),避免把 UI 標籤當成待擷取的來源頁
loop_apidoc/url_adapters.py resolve_fetch_url(純函式、不做 I/O):在發出請求前,先把文件 URL 對應到真正承載內文的表示形式。HackMD 筆記 URL 會解析成其 /download 原始 Markdown 端點,避免抓到 JavaScript 外殼而靜默失去來源;其餘一律維持 HTML 撈取
loop_apidoc/source_facts/ 擷取閘背後的確定性來源事實盤點:markdown.py(純掃描端點宣告、參數表與圍籬範例區塊)、collect.py(讀取 manifest 指名的 Markdown 來源,本套件唯一讀檔出口)、gate.py(以事實對照擷取 JSON,並沿 schema_ref 遞迴解析進 inventory.schemas)、deferral.py(攔截佔位式答案;分兩層,英文以詞界比對)。已接進 agentcli/gate.py,因此 verify-extraction 與 assemble 都會對靜默遺漏 fail closed
loop_apidoc/foundry/ 專案本地 .foundry/api/ 治理：normative assets 保持 immutable，feedback case 保留一次綁定的 decision；Effective current pointer 綁定包含所有宣告欄位、經 strict validation 後的 canonical asset 與三份 artifact digest，successor ID／digest pair 形成逐節驗證的 immutable hash chain，未知欄位與任何歷史竄改都拒絕；全域 current 保持 normative
loop_apidoc/review/ 本機單使用者 review 工作台：自動匯入 candidate、比對 current／baseline、保存結構化 handoff，並在人工明確核准後讓 Foundry 更新 current
